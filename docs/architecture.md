# Architecture

## Owners

| Owner                      | Responsibility                                                                  | Main location                                  |
| -------------------------- | ------------------------------------------------------------------------------- | ---------------------------------------------- |
| Application                | Boot, input, loading, pause, fixed-step scheduling and persistence operations   | `src/application.ts`                           |
| Simulation and GameSession | Gameplay outcomes, transitions, encounter state and checkpoint capture/restore  | `src/core/`                                    |
| Content                    | Gameplay definitions, scene parsing/resolution and explicit visual requirements | `src/content/`                                 |
| Presentation               | Interpolation, animation, camera rendering, lighting and GPU resource disposal  | `src/presentation/`                            |
| Developer sessions         | Editor/preview controls, temporary state, mounted requests and cancellation     | `src/editor/`, `src/sandbox/`                  |
| Storage adapters           | Shared validation, browser storage and atomic desktop writes through Bridge     | `src/platform/`, `electron/`                   |
| Asset tools                | Source preparation, immutable delivery, workspaces and cache leases             | `tools/assets/`                                |
| Development tools          | Guide discovery, checks, test selection, builds and preview processes           | `tools/` (asset operations in `tools/assets/`) |

## Application lifecycle

### Hosts and inspection

Game and Dev Preview, including its effects fixture, share the Application lifecycle. Dev Preview's shell retains per-fixture state; opening an inspector is separate from entering dedicated animation/calibration rendering. Preview state uses validated session storage and storage-free bridges, never player checkpoints/settings. Mounted developer sessions dispose their requests, observers and rendering work together. Remounting the editor closes the previous host before replacing its DOM; shutdown revokes property event handlers, closes dialogs and makes the retired controls inert before peer cleanup. Its frozen inspection facade stays bound to that session, including after a successor mounts.

Dev Preview startup failure and normal shutdown close the same mounted lifetime. Closing revokes controls and inspection commands before attempting every peer cleanup; a failed renderer destructor cannot retain shell listeners or loading UI. A retired mount removes an inspection global only when it still owns that value. Failure leaves a retry action, while completed asynchronous work cannot revive the closed fixture.

SceneContent binds scene composition and asset requirements to the ContentRegistry that produced them. Application owns the active session and SceneContent together; its registry, checkpoint validation and New Game derive from that binding. Switching registries requires a read-only application; developer hosts provide storage-free bridges. Game retains the registry selected by its storage adapter.

Application exposes a frozen SessionView for inspection and checkpoint capture, keeping GameSession's replacement commands private to its owner. Its `sim` property borrows the stable SimulationView, with no gameplay command methods and deeply read-only actor, drop and collection types. Ordinary hosts execute gameplay through Application, which steps its owned Simulation and executes player interactions. Developer controls and inspection tools use synchronous `editPreview` callbacks, admitted only in a read-only application with an accepted room and no loading work or pending session operation; disposal closes that admission. Developer step hooks and new-session preparation retain explicit mutable access for fixture setup and replay. Borrowed views remain tied to their original room after replacement. Developer replacements submit SceneContent and a new-session specification or checkpoint; Application constructs the matching GameSession, assigns its generation and creates feedback before acquisition. Checkpoints are validated and detached at admission. New-session preparation may configure preview actors synchronously; it cannot choose room identity or generation. The public API never transfers a caller-owned GameSession into the active application.

`src/dom.ts` renders literal HTML templates with escaped text/attribute values and native node slots. Menu and editor controllers own listeners, focus and cancellation; templates retain native control identity without owning session state.

Game mounts `createGameUI` against its own stage element. That mount owns pause and adventure state, status timers, DOM listeners, audio controls and event subscriptions. Closing the mount removes its dialog and revokes handlers before Application shutdown; pending command completions cannot redraw or report into a later mount. No Game UI state is shared at module scope.

### Startup

Application startup owns one resource graph and frame scheduler for its lifetime. Concurrent, reentrant and repeated `boot()` calls share the same startup promise. Failure closes the application and its acquired resources; retry creates a new Application. Disposal rejects `boot()` promptly even when transport or renderer preparation never settles. The startup graph continues observing its acquisitions and releases late results; cancelling the caller does not transfer or abandon resource ownership. Presentation construction transfers ownership only while the application remains active; a factory result returned after shutdown is disposed before input can mount. Settings and checkpoint waits discard late results. Runtime opening borrows the host lifetime through policy and registration reads, aborts transport, and closes its staged runtime on cancellation before transfer. The editor passes its own startup lifetime to the same runtime boundary. Closing a loading playtest releases startup admission and discards cancellation feedback, allowing immediate re-entry.

Game selects checkpoint startup and Game asset policy explicitly; developer hosts default to a new session and full authoring registration. Settings and checkpoint reads begin together with runtime opening. A validated checkpoint selects the initial room before acquisition, avoiding a discarded starting-room render. Retained and room batches acquire concurrently with shared failure cancellation; animation flow and lighting preparation overlap. Game prepares its renderer before asset acquisition and uploads verified textures as their decodes finish, overlapping acquisition with GPU preparation. The preparation owner revokes upload callbacks on disposal; presentation construction transfers renderer cleanup to GamePresentation. Developer factories may omit early preparation. Readiness requires complete preparation and a rendered frame. Session replacement commands cannot enter during startup. Empty or unavailable checkpoints retain the initial session and storage errors remain visible.

FrameScheduler closes its timer, animation callback and focus listeners before reporting a frame or focus-reset exception. Application and editor frame faults close their mounted resource graph and leave visible failure feedback; they cannot retain a ready session with a stopped render loop. Construction failure also removes scheduler listeners. Recovery creates a new host lifetime.

### Desktop profiles

`electron/session.ts` owns desktop navigation and storage profile admission together. Launch closes storage admission before draining the current profile and rejects overlapping launches. Destination storage becomes available during navigation so its boot can read settings; main authenticates IPC against that destination's entry. Failed navigation closes and drains destination storage before restoring the previous profile and page. Failed recovery blocks storage until a successful launch. Window closure permanently revokes launch and storage admission and returns a shared drain promise for admitted I/O. `electron/shutdown.ts` holds process quit until that drain settles, including closure during startup navigation. Repeated quit requests share the same shutdown; quit also prevents new startup admission.

### Session operations

Application owns one current session operation spanning checkpoint reads, room acquisition, commit, persistence and completion. `SessionOperations` owns admission, cancellation, completion and terminal disposal; operation bodies borrow a standard AbortSignal and use the shared cancellation-aware read helper. Admission installs the next owner before aborting its predecessor, so a newer intent submitted by a synchronous cancellation callback supersedes the admitting operation. Loading callbacks are also checked before operation work begins. Completion clears only its own ownership; disposal closes admission and clears ownership before aborting callbacks. A newer Load, Restore, Reset, New Game, transition or developer room replacement supersedes a replaceable operation. A forge purchase reserves exclusive operation admission before loading callbacks; later commands cannot supersede its submitted write. The operation owner releases this reservation on completion or shutdown. Superseded operations cannot commit, resume play or start an autosave; expected cancellation stays out of error feedback. Transition plans cancel immediately. Storage reads stop blocking loading on cancellation and discard late results. Disposal cancels session operations and the separate retained/preview asset lifetime. Writes already submitted remain ordered by the storage adapter.

Command completion and acquisition draining have separate lifetimes. Supersession or disposal settles the command caller immediately, including developer preview selection, without waiting for obsolete transport or native decoding. `SessionOperations.run` returns only a boolean or void outcome, so cancellation cannot abandon a resource transferred as its result. The operation body remains observed until settlement and owns its staged resources through cleanup; it checks admission before accepting results, committing gameplay or invoking host callbacks. ResourcePool and AssetRuntime continue draining cancelled acquisitions and releasing late results under their existing ownership contracts. A completed cancellation does not establish that native work or cleanup has finished.

Application privately owns `Persistence` for checkpoint and settings I/O; UI and developer inspection borrow only its frozen error view. Each checkpoint write rechecks the application's accepted room and read-only policy at admission. Disposal closes storage admission before cleanup callbacks, rejects pending callers without waiting for the adapter, and discards late results and errors. Already admitted writes finish under adapter ownership; a stopped manual Save cannot submit its later settings write or publish feedback. Settings reads and writes share this lifetime while remaining available to read-only preview applications.

`LoadingScopes` separately owns interaction blocking and overlay feedback: cancellation retires a session operation's scope immediately, while its resource acquisitions continue settling and releasing late leases. Room operations pass cancellation through presentation preparation and stop waiting for obsolete companions; the companion owner releases staging before advancing its selection queue. A recovered accepted room can play before obsolete acquisitions settle. Independent retained/preview loads keep their own scopes. Synchronous successor admission shares the existing overlay; retired completion cannot clear new input, reset its frame clock or repeat loading feedback. Retiring a loading scope cannot restore revoked room acceptance; a partially rebuilt room remains blocked until successful recovery.

### Room transactions

Simulation steps return death-reset and transition requests without replacing the session. Application executes death recovery through the same room transaction as manual reset; it publishes reset feedback and autosaves only after acceptance. Developer command hooks can return an explicit reset request, which stops the current fixed step and uses the same room transaction. A hook that starts a session operation also stops that step before consuming input or advancing gameplay. Preview actor overrides remain mutable, while Simulation's area and generation are read-only. Headless session replay owns its GameSession directly and explicitly commits reset requests without renderer preparation.

GameSession prepares every travel, rest, reset and checkpoint restore as a single-use RoomPlan. Preparation validates admission and constructs the destination simulation, area snapshots and progression before Application acquires renderer resources. The candidate stays private to GameSession; its public plan exposes only destination, source generation and start feedback. Failed preparation preserves the active simulation and progress. Cancellation discards the candidate, and superseded or already consumed plans cannot commit. Application checks the plan before revoking room acceptance; commit transfers the prepared state without reconstructing gameplay. Headless callers use the same commit contract, with synchronous reset/rest/restore conveniences preparing and committing immediately.

GameSession owns simulation, inventory, visited areas, discovery and counters in one accepted RoomState; commit swaps that owner once. Every room candidate receives detached inventory, including travel, rest and reset. Simulation borrows read access to its own inventory and write capabilities checked against the accepted inventory owner. Retired rooms cannot award loot or consume potions in the accepted session. A pending plan suspends inventory writes, equipment/salvage commands and campfire discovery; cancellation restores source-room admission, and failed candidate construction preserves the previous plan. A prepared forge purchase also occupies this pending owner: stepping, inventory commands, loot/consumption and onboarding writes stay suspended until its single-use commit or cancellation. Each read of its candidate checkpoint returns detached data. Headless room replacement supersedes the purchase; cancelling that stale purchase cannot clear a successor room plan. Application additionally holds exclusive operation admission across durable purchase writes. Public progression properties have no setters, discovery reads are detached sets, and checkpoint admission remains the path for headless state setup.

Room replacement has a separate acceptance barrier. Before committing gameplay changes, Application revokes room acceptance; committing a generation immediately aborts old event feedback. Acceptance returns only after renderer rebuilding and companion preparation both succeed under the current operation. A failure after commit pauses the application and blocks simulation steps, renderer updates, resume and checkpoint writes until a successful Reset, Load, Restore, New Game or developer room replacement. An empty Load does not recover the room. Failures before commit preserve the previous accepted room. Asset leases remain owned through failed rebuilding as described below; recovery does not roll back committed gameplay.

## Scene content

### Direction, camera and input ownership

`src/content/headings.ts` owns world-yaw heading identifiers and selection, shared by combat, authored action timing and asset clips. Gameplay never loads camera calibration or asset delivery at runtime; animation helpers may borrow type-only clip contracts. `src/assets/camera-contract.ts` binds baked projection to runtime framing, `src/assets/camera-calibration.ts` owns preparation calibration, and `src/assets/sprite-registration.ts` maps source trim rectangles around their anchors. Asset validation consumes these definitions directly.

`src/presentation/camera.ts` owns Three.js camera construction, viewport constraints, projection and screen-relative movement. Camera framing jointly fits the viewport inside the finite rendered `sceneBoundary` and keeps the complete hero below the upper controls. It adjusts the center and zoom together; no silhouette correction can expose space beyond the scene. Artwork layout reserves a playable margin for the hero inside the full painting, while rendering and camera coverage retain its original footprint. Checkpoint admission moves positions in the former outer margin onto nearby framed ground only when the original floor and connecting segment are clear; progress is preserved. `keepHeroVisible` controls authored composition bias only; final scene coverage and hero framing apply universally. If an impossible focus lies beyond the painting, coverage remains mandatory. `src/input.ts` adapts DOM input and pointer projection into gameplay commands under Application's lifetime. Rendering and browser input do not live in the gameplay model. Camera and direction algorithms remain shared across Game, editor and preview consumers through their respective owners.

Combat commands carry one ordered `actions` list (`sword`, `lantern`, `dodge`), shared by input, previews and replay recipes. Input queues each press once; potion use remains a separate command flag.

### Content acceptance

ContentRegistry clones and deeply freezes gameplay definitions before validation. Its private lookup indexes and public definition snapshot share the same accepted objects; callers retain editable drafts. Scene composition separately snapshots visual definitions and freezes their derived asset requirements, so draft edits cannot change live geometry, checkpoint validation or rendering requirements. Registry acceptance validates every hero entry and the complete enemy spawn jitter segment against actor clearance, so Game, transitions, headless sessions and editor playtests cannot bypass placement validation. Replace content by constructing a new registry and scene composition. Editor renames follow scene acceptance rather than mutating the active simulation.

### Scene documents and ground interaction

Version 5 scene documents own floor, scenery, camera, surrounds and gameplay geometry. `src/content/scene-document.ts` parses them; `src/content/world-art.ts` resolves area geometry, colliders, visuals and asset requirements together. `src/content/world-visuals.ts` owns visual types, resource requirements and framing helpers.

Editor history forks share frozen scene snapshots and copy only their undo/redo stacks. View acceptance runs only when a transaction changes the document; history-only changes still commit their undo/redo state.

The optional `groundInteraction` block binds normalized image contours to an exact asset hash, frame and dimensions; independent world-space polygon footprints resolve into ordinary blocking props. Depth anchors or left-to-right piecewise boundaries belong to presentation. `src/content/floor-layout.ts` owns both artwork/world mappings and resize reprojection. Image coordinates start at the top left, with Y increasing downward; floor rendering converts them to bottom-left texture UVs at the presentation boundary.

Scene documents allow 4 MiB; fragments retain 64 KiB. Saved contours need no model to load. Editor saves additionally retain immutable authored revisions in `authoring/ground-profiles`, independently of scene and asset-library lifetimes. `src/content/ground-profile.ts` owns explicit artwork reassignment and floor reprojection; changed image content requires alignment review. Ground replacement requires clearing or reauthoring interaction data.

`src/presentation/ground-occlusion.ts` owns the source-sized coverage/depth atlas, fragment masking for actors, placed props, fixture flames and drops. Only heroes and enemies receive hidden silhouette outlines; props and drops disappear behind the authored foreground. Contact shadows are clipped away from upright scenery baked into the painting. Contact and cast shadows multiply the receiving colors so they cannot brighten black ink. GPU size limits reject unsupported scenes explicitly.

`src/content/scene-placement.ts` rejects authored enemies and gameplay props that overlap painted collision footprints or occlusion silhouettes, including a clearance margin and spawn jitter. Noninteractive scenery may sit behind painted silhouettes, while its base still respects collision and the floor edge. Mask holes remain valid clear ground. Ground decals and explicit attachments retain their artwork roles; walking beneath a canopy remains governed by collision. Scene resolution enforces this in Game, editor edits and playtests; the editor ghost turns red on masked ground.

Parsing protects technical validity; design profiles produce advice under [scene guidance](scene-design.md).

### Area state and reconstruction

`src/core/area-state.ts` owns the area checkpoint schema, registry validation and encounter-respawn policy. Simulation captures detached area state and accepts saved state only during construction, through the same validator used by full checkpoint admission. It reconstructs enemy positions, health, death poses, local alerts, pickups, claims and drops together. Action clocks, movement requests and object animation ticks remain transient.

GameSession retains area snapshots and selects when to revisit or respawn them; it never reconstructs enemy actors or assigns simulation collections. Rest and death combine fresh encounter state with retained claims, pickups and non-enemy drops. Room travel and checkpoint loading retain local alerts, so reconstruction cannot silently lift combat restrictions. In current version 9 checkpoints, an omitted optional `alerted` spawn-ID list starts without local alerts. Earlier checkpoint versions are incompatible under [saved-state admission](#change-saved-state).

### Ground loot

Each GroundDrop stores one reward stack with a stable source/reward-index identity. Admission verifies the stack against its claimed container or defeated enemy. Collecting one stack leaves its siblings in the room and checkpoint; rest retains container stacks and discards enemy stacks. GroundLootLabels projects item buttons through the current camera and deconflicts their screen positions. PickupPlan owns only a transient route intent; explicit movement/actions, pause, replacement and death cancel it. Application rechecks authoritative interaction reach before awarding a stack.

### Collision and navigation

`src/content/collision.ts` owns footprint geometry, circular clearance, swept contact queries and corrective placement projection. Registry acceptance, checkpoint validation and navigation share position clearance; spawn jitter, route segments and smoothing share segment clearance. Visibility breakpoints reuse those footprints and rounded clearance, while `src/content/world.ts` supplies surface-height breakpoints. Sanctuary traversal classifies the resulting intervals, including narrow terrace corners and gaps in scenery. Projection is a best-effort correction and never proof that a position is valid. Checkpoints use the same minimum actor radius as movement. Footprint caches retain only immutable props.

`src/core/navigation.ts` owns movement sliding over those swept contacts and deterministic eight-neighbor A* at 0.2 world units. Route diagonals cannot cut corners. Walking, dodging, separation and editor Walk hero use the same sweep. Enemy pursuit replans at most every 15 ticks and requires unobstructed melee contact. Transient targets and route diagnostics never enter checkpoints.

`src/core/encounter-behavior.ts` owns local awareness, group alerts, sanctuary/leash policy and enemy intents. It borrows read-only actors and never moves them or starts combat actions. Simulation applies those intents and coordinates action resolution and event ordering. The shared actor model lives in `src/core/actor.ts`.

`src/core/movement-plans.ts` owns room-local navigation and transient routes for manual commands, home return and pursuit. Hero and enemy routes use separate clearance caches. Enemy traversal borrows the encounter owner's sanctuary policy for positions and segments; direct paths, grid edges, smoothing and actual movement obey that policy together. Sanctuary exclusions respect height and obstruction, while hero routes remain open. Switching automatic intent replaces its route immediately; moving targets within the same intent retain the 15-tick planning cadence. Manual targets take priority until completion or cancellation. Awareness never edits route caches. Simulation creates both owners for its immutable area, clears both on repopulation, and captures/restores only awareness through area state. Navigation diagnostics borrow detached route data without initializing the planner.

### Combat actions and fixed-step ordering

`src/core/command.ts` owns the command schema and inferred public type for live input, Simulation and recorded replay. Simulation admits commands through its generation and finite-point adapter before combat sees ordered actions. An explicit action list, including an empty list, takes precedence over legacy attack/ability/dodge flags; stale commands cannot move, use potions or queue actions.

Application admits each frame against a clock epoch and current freeze state. Pause, loading, focus changes and simulation policy reset the epoch. Hooks and feedback may revoke admission: recheck before each step and after external callbacks; an obsolete frame cannot commit another command, request a reset or transition, or animate elapsed time. Disposal stops all remaining renderer and host callbacks. Already committed gameplay retains its normal save behavior while the same room remains accepted.

`src/core/combat-actions.ts` owns attack/dodge/ability admission, input buffers, action entry and interruption, hit geometry, damage, invulnerability, stagger and recovery. Each Simulation constructs one combat owner for its immutable area and generation. The owner borrows current actors through a live capability view, so repopulation and developer actor replacement cannot leave it targeting retired actors. It does not retain a second actor collection or advance action clocks. Actor definitions may give enemies poise: direct Physical damage preserves their current action, while the lantern’s initial Burn hit still interrupts and stuns. Burn ticks never interrupt. Visual bindings own optional actor scale; sprite, contact shadow, body-aim capsule and authored spawn-envelope validation consume the same scale. Lantern bursts give surviving enemies a short recoil during their existing stun. Actor-keyed impulses remain private to this combat owner and use supported movement; checkpoints save resulting positions without replaying unfinished impulses.

Simulation owns the fixed-step sequence: cooldowns and previous positions, hero command admission and locomotion, then each actor's recoil, enemy intent and action resolution. All actor ages advance together after combat, preserving dodge protection at the same action tick regardless of actor iteration order. Separation, pickups, room-clear detection and exit requests follow. Combat uses explicit room capabilities for supported movement, event emission, enemy awareness, death drops and breakable claims; inventory, navigation plans, checkpoints and room replacement remain outside its contract. The existing Simulation action commands delegate to this owner for developer setup and headless callers.

Game UI shows a contextual lantern prompt while an unlearned lantern lesson has a reachable enemy within burst range. It follows the mounted UI and current session's onboarding state, hides during pause, loading and death, and clears when the ability is used or the threat leaves range.

### Editor documents and playtests

`src/editor/ui.ts` owns fixed editor panels and dialogs; controllers bind behavior and render changing content inside them. Game and preview styles belong to their respective stylesheets; `src/style.css` owns only the document reset.

RoomPresentation uses authored artwork for scenery and exits. Its untextured fallback provides terrain and a grid for systems diagnostics; scenery requires an explicit visual definition. Scene art findings own resolved attachment checks and solid intersections; the renderer overlay and asset regressions use the same coplanar source-coverage validator.

Editor playtests use the world-art resolver through `src/content/draft-gameplay.ts` and run the shared Application with a storage-free bridge. Optional enemy, exit and health-pickup placements become plain runtime definitions; core owns collection and checkpoint state. Core does not load live scene documents. Original artwork and preparation remain separate from placements and gameplay timing.

Editor startup failure uses the same complete shutdown path as normal disposal. `src/editor/preview-images.ts` owns thumbnail and animated-preview image loading: at most six active image requests, a shared LRU cache capped at 48 pages and 64 MiB of decoded RGBA pixels, retryable failures, and latest-request canvas acceptance. Painted thumbnails retain no decoded source outside that cache. An open animation borrows an explicit playback lease that retains only its current page, including oversized atlases that would otherwise reload every frame. Each canvas request claims its pending source. Replacing a canvas request or closing playback settles that reader immediately; the final reader removes queued work or cancels active image transport. Other readers keep the shared load. A successor for the same source claims it before retiring its predecessor. Late completion cannot cache retired pixels or remove a newer request. Closing or replacing the preview releases its displayed-page lease; editor shutdown revokes all playback leases, cancels active image loads and settles queued requests. These images do not borrow GPU pack leases.

`src/editor/gestures.ts` owns one captured pointer gesture across viewport dragging, marquee selection, geometry handles, transform controls and ground strokes. Tools borrow leases; completion releases capture before committing. Document operations suspend admission and cancel the current preview before editing or replacing scenes. Tool changes, focus loss, hidden documents, lost capture and disposal revoke the same lifetime, so late releases cannot apply old targets to replacement documents. Ground multi-click proposals and AI requests retain their separate tool-owned lifetimes.

EditorDocument owns committed editor history. Single-object and batch transforms share one support-ordered transaction and one undo entry. EditorHistory validates attachment resolution and scene constraints before accepting its first snapshot. It stores deeply frozen scene snapshots; edits clone a mutable draft and validate the completed change. Selection resolves detached placements without repeating full scene admission. Read-only consumers receive a frozen history facade rather than the live history owner. A staged history is forked before validation and rendering, so retained edit callbacks cannot mutate an in-flight candidate or the accepted history. Undo/redo share only immutable scenes; fragments and resolved visual data are detached editable outputs. All edits, undo/redo, imports, opening scenes and recovery restores stage a candidate and validate gameplay before applying it to EditorView. Only view acceptance commits the candidate; selection and local recovery updates follow that commit. Failed application restores the previously committed view and preserves its undo/redo history. Document callers stop waiting immediately on editor shutdown, including during view rollback; EditorView retains ownership of acquisitions and late cleanup. Late view completion cannot commit history.

EditorView owns placement-preview acquisition separately from room assets. Changing or clearing placement aborts the old claim and settles its caller without waiting for transport; late packs release before they can build a sprite. Ownership is consumed before abort or destruction callbacks, and reentrant selection retains the newest request. Sprite disposal precedes its pack release.

EditorView exposes its renderer and simulation only while an accepted room is available. Rebuilding revokes that acceptance before mutating the renderer; acceptance returns after warming and companion preparation succeed. If rebuilding and document rollback both fail, frame rendering and scene interaction remain blocked until a successful apply recovers the view. Failures before renderer mutation preserve the previous accepted room. Disposal discards pending candidates without reopening the view. Inspectors and composition tools read the committed snapshot; edit callbacks receive a separate mutable history. Saving reidentifies the accepted history without adding an undo step.

`src/editor/project.ts` owns scene file revisions, dirty-state baselines, authenticated writes and workspace-scoped local recovery. Open, import and recovery restore change file metadata only after EditorDocument accepts the replacement. Selecting a recovery leaves the active file identity intact until restoration succeeds; unreadable recoveries remain available for export or dismissal. Successful server saves accept their revision before optional recovery cleanup, so unavailable browser storage cannot leave the editor using an obsolete revision. The saved baseline records the document actually written, preserving later edits as dirty. EditorProject owns operation admission across transport, document acceptance and file metadata. Concurrent file operations reject before starting; replacement also blocks edits and recovery selection. Edits remain available during save transport, then save acceptance closes edit admission and waits for the admitted edit to commit or roll back before reidentifying history. The UI owns confirmation and feedback; the project owner receives its request, storage and cancellation dependencies explicitly. Project shutdown settles file operations, response-body reads and authenticated tool requests without waiting for transport. Tool-request cancellation combines its own signal with the project lifetime. Closed projects reject recovery commands and stop accessing local storage; late responses cannot change file metadata or recovery.

### Game content selection

Game runtime and builds share the content and asset selection in `src/content/game-content.ts`, which resolves the selected orchard, clearing, forge and chapel authored documents. Saving under `authoring/scenes/` does not add a scene to Game; follow [Add an area or enemy](#add-an-area-or-enemy) to register it. Authored scenes are replaceable; developer presentation fixtures and gameplay test arenas own their setup independently. Asset preparation and runtime delivery retain their curated catalog independently of scene selection.

## Runtime resources

`src/content/polygon.ts` owns shared clipping, intersection, boundary and edge-distance calculations for collision, authoring and presentation. Screen-space consumers map their vertical axis to Z at that boundary. `borrowedView` in `src/content/snapshot.ts` projects explicitly selected live properties with frozen getter descriptors; hosts retain only the commands named by each view.

GamePresentation coordinates RoomPresentation, ActorPresentation and SceneLightingRenderer. ActorPresentation returns animation feedback as frame data; GamePresentation publishes it only after actor updates, scenery, effects and rendering finish. Synchronous observers can then replace or dispose the application without invalidating an in-progress frame. Closed presentations reject further rendering, and asynchronous shader preparation rechecks lifetime before borrowing scenery again. Preserve renderer ownership and disposal. The existing Three.js math and content/assets dependencies are intentional; a new engine or UI framework is unnecessary.

Painted shadow contours share one submission per authored region, retaining their original triangulation, holes and depth bends. Character beauty, shadow and focus materials declare animation blending before their initial draw. Lighting preparation uploads decoded companion textures before readiness, checking cancellation and disposal between uploads. CombatFeedback submits clipped effect representatives during the first covered beauty draw, then hides them while retaining their shader programs between bursts; reset preserves them and disposal releases them. The flare ring receives a borrowed primer in the same pass. Preparation must use the actual postprocessing target and light topology: asynchronous compilation against the default framebuffer alone prepares different variants. Local lighting keeps five shader slots admitted while enabled and primes their cube storage during the covered room draw; inactive slots stop redrawing, while active slots continue reflecting every caster change. This avoids room-wide shader variants and cube allocation on first lantern activation. Renderer timing queries are opt-in through SceneLightingRenderer and never run during ordinary Game frame submission.

Game keeps its startup cover and readiness marker pending through item-art preparation. HUD, loot and adventure panels share cropped drawing promises for the same runtime and UI lifetime. Preparation is serial to bound decoded image memory; abort revokes object URLs, clears the cache and prevents retained artwork functions from borrowing the runtime again. Missing optional drawings retain the existing error fallback.

Presentation borrows `SimulationView` from `src/core/simulation-view.ts`, with read-only actors, collections and current-tick fields; it cannot call simulation commands. Application and editor pass the stable `Simulation.view` facade. Views are live borrows, not retained snapshots, and TypeScript protects nested state from writes. Navigation diagnostics return detached data without initializing gameplay navigation. Developer render hooks use the same view; deliberate gameplay overrides remain in the application step hooks.

### Transient effects

CombatFeedback uses interpolated action time for supplied Flare, Lunge and Dodge drawings. Flare has a separate warm light slot, rising for 100 ms before damage and fading over 250 ms afterward; it does not alter the steady lantern or damage rules. Guiding wind crossfades route snapshots, runs for eight seconds in a twelve-second cycle and shares a local breeze with foliage and smoke. Developer visual comparisons select autumn gust, falling leaves or their combination, and dust, leaves or combined Dodge trails.

### Asset ownership and disposal

Application, the editor session, EditorView and DraftPlaytest revoke availability before shutdown callbacks. Editor session shutdown attempts every mounted tool, observer, preview, renderer and runtime even when a peer fails. DraftPlaytest consumes overlay and application ownership before attempting both cleanups; failure cannot leave a retained preview running or prevent dialog removal. Their teardown, GamePresentation and the asset owners attempt each peer cleanup in dependency order. Renderer disposal is attempted before borrowed asset leases release; pool closure invalidates all claims, including pending decodes. `src/assets/cleanup.ts` owns synchronous cleanup fault containment: one failure is rethrown unchanged, multiple failures form an AggregateError, and unwinding an operation preserves its original error as the cause. Cancellation listeners report cleanup failures through the pending acquisition promise rather than throwing from EventTarget dispatch. Failed shutdown remains terminal; repeating disposal does not rerun consumed ownership. This contract extends through InkRoom, ActorSprite and PropContactShadows: each consumes its collections before callbacks and attempts all owned geometries, materials, meshes and sibling sprites even when a Three.js disposal listener throws. This guarantees cleanup attempts, not successful destruction by a failing external callback.

TextureDelivery owns each decoded texture from parser completion through dimension validation, configuration and upload; every failure before transfer destroys the staged texture and bitmap. Parser initialization failures retire their shutdown waiters, and shutdown registers late transcoder cleanup before attempting external destruction.

`DisposalScope` registers renderer resources as construction acquires them and consumes cleanup in reverse dependency order. Game, lighting and Dev Preview share this shutdown path with failed construction; preview cleanup cannot prevent base renderer shutdown. Actor visuals and room terrain use the same scope from their first geometry/material allocation, including resources not yet attached to the scene graph. Failed actor attachment removes its staged nodes and releases every allocation; replacement retires the previous visual through its own scope. Failed room construction closes scenery and terrain ownership immediately, preserving the construction error if cleanup also fails. Room resets detach receiver, shadow and focus ownership before attempting peer destruction.

AssetRuntime snapshots its catalog and accepts fetched and seeded manifests through one identity-checked boundary. Accepted manifests, frames and clips are deeply frozen and exposed as read-only data; parsing and preparation retain mutable `ManifestDraft` values. Consumers cannot change validated page identities, geometry or timing. Shared manifest admission precedes transport callbacks, and an obsolete request failure cannot evict a seeded successor. Runtime shutdown settles metadata readers without waiting for transport; late responses remain observed and cannot register pages after closure.

`src/assets/acquire-batch.ts` owns deduplication, progress and failure cleanup for ResourcePool and AssetRuntime batches. AssetRuntime exposes pack-batch acquisition for Application and the editor; completed packs stay owned until transfer. Failure or cancellation immediately releases completed packs and cancels pending texture claims, while acquisitions still settle and dispose late results. Independent consumers retain their own claims; batch release is idempotent. Callers validate a completed batch before transferring it to `SceneAssets`, the shared room-lease owner for Application and EditorView. Its stable read-only view exposes the installed batch; failed synchronous rebuilding exposes all retained batches so preview inspection can resolve either generation. Installation consumes the batch even if synchronous renderer rebuilding throws; both generations remain leased because a partial renderer may reference either. A successful rebuild releases superseded batches; renderer disposal precedes closing SceneAssets. Failures in later asynchronous preparation leave the installed batch owned for retry or document rollback. Editor replacements acquire a complete batch, sharing decoded textures through ResourcePool rather than manually transferring individual leases.

Each room batch includes its SceneContent's initial assets and area requirements, so replacing content acquires the new hero and feedback packs and releases the old source with the room. Application separately owns explicitly retained assets and preview batches through another SceneAssets owner. Preview operation admission precedes loading callbacks; newer selections cancel obsolete texture claims and retire their loading scopes without waiting for transport. Warming and selection recheck that admission before acceptance. Failed selection retains both batches because rendering may already borrow the candidate; a successful successor or renderer shutdown releases them. Reentrant SceneAssets installation cannot retire its successor's batch. Presentation borrows read-only pack views without release capability. Its pack map derives from those ownership groups, including preview overlap with a room or retained asset.

AssetRuntime shares manifest transport for its lifetime; each pack consumer can cancel its wait without blocking batch completion or cancelling another consumer. Disposal closes manifest waits and ResourcePool. ResourcePool admits all batch claims and installs cancellation before invoking loaders. Each identity has one registered owner before external code runs, so synchronous reentrant acquisition shares that owner; cancellation retires the batch’s claims and prevents unstarted peer work while independent consumers retain their claims.

Each pooled identity owns a cancellation signal passed through AssetRuntime to texture delivery. Releasing its last claim revokes that signal after removing the owner, cancelling downloads and queued decodes; a surviving claim keeps shared work alive. Active native bitmap or compressed decodes retain their slot until they settle, then discard cancelled results without GPU upload. Disposal during a loader closes every owner before peer work can start. Pool closure invalidates all leases, releases loaded textures once, and disposes late decode results before acquisition can succeed. Closed runtimes reject reads, seeding and acquisition. Failed pool batches release their claims immediately and settle pending peers before reporting failure; other consumers retain their own claims. Presentation must dispose before its runtime owner closes.

`src/assets/resource-cache.ts` owns pending reader claims and bounded LRU retention for bundled bytes, decoded audio and editor preview images. Each consumer supplies its memory weight and budget; audio leases pin buffers through playback, while an open preview retains its displayed image separately. The cache admits readers before invoking loaders, and preview transport accepts the same AbortSignal as its decode queue. Cancelling one reader preserves its peers; cancelling the last reader unregisters the download before aborting transport, so recovery can start a fresh request even if old transport never settles. Late completion cannot cache obsolete bytes or unregister a successor. AssetByteSource admits only verified bytes into its 32 MiB cache.

### Lighting resources

Interior and exterior cutouts share source-aware local reveals. Reveal animation keeps material opacity and depth-writing policy stable; scenes no longer fade whole assemblies. `SceneVisualEffects` owns fixture flame pose, timing and light modulation; `InkRoom` owns the flame sprites and their disposal. Shadow casters borrow existing scenery sprites and reject missing artwork instead of generating substitute geometry.

Lighting preparation begins through `prepare`, rather than constructor-started promises. Ground artwork uses the registered floor material directly; the retired procedural stone-height/UV pipeline is absent from rendering, preparation and delivery. Failed preparation remains retryable. `BitmapTexture` owns the animation-flow texture: concurrent and repeated reads share one texture, failed decode or upload releases acquired resources, and disposal cancels transport, settles waiters and releases late decodes without upload. Lighting manifest requests carry the renderer lifetime; normal bitmap requests also carry their room selection's lifetime. `src/presentation/normal-library.ts` retains selected `BitmapTexture` owners through `ResourcePool`; byte accounting derives from the accepted texture map. ResourcePool batches release every sibling claim on the first acquisition failure and preserve that failure even when earlier identities reject from cancellation. Normal replacement uses this same policy, so failed staging cannot hold the selection queue behind an unfinished native decode. Replacement retains current textures until all requested companions load successfully; failed batches attempt cleanup of every new texture and preserve acquisition errors if cleanup also fails. Cancellation settles queued and active callers, releases completed staging and advances the selection queue without waiting for native decodes. Normal companions and editor preview images use `DecodeQueue` for bounded admission and shutdown; each owner selects its limit. A renderer-wide eight-slot queue retains active normal decode slots until settlement, bounding overlapping cancelled selections. Late images close before entering staging and cannot replace a recovered selection. Successful replacement transfers the complete selection before retiring removed textures, so cleanup failure cannot leave disposed resources installed or stale byte accounting. Disposal consumes ownership before callbacks and closes late acquisitions.

`SceneLightingRenderer` owns the runtime cohesion treatment. `IllustratedLighting` groups eligible cutout values and samples four neighboring source texels only inside opaque prop interiors, protecting alpha contours and deep ink. Actors retain their existing animation sampling. The existing finish pass shares a restrained palette across painting and cutouts. `PaintedEnvironment` lazily renders a maximum 128 × 128 unlit ground-color field when bounce first becomes active, reads it back once and bilinearly samples its cached bytes per sprite at foot registration. No bounce texture is sampled per fragment. Room reset clears the cached field and borrowed source/mask textures before asset release. Contact cores alter only the existing actor and instanced prop shadow materials; they add no meshes or draw calls. `defaultLook` owns the four enabled defaults, while Dev Preview persists each independent override.

Optional `look.shadeZones` describe up to eight world-space circular patches of ambient shade already painted into a floor. The shared illustrated-lighting shader applies their smooth falloff to placed scenery and actors, using each sprite's foot registration. Overlaps use the strongest shade; the painted floor is not shaded twice, and local light and emissive artwork remain luminous. Scene replacement clears prior zones. Interior scenes retain contact and local-light shadows without directional outdoor casting.

The hero lantern illuminates nearby scene surfaces with broad distance falloff, without a billboard glow. Its source follows reviewed native drawing sockets in `src/content/hero-lantern-sockets.json`, transformed with the displayed frame's registration, stabilization, animation blend and mesh transform. These coordinates belong to the current hero handoff; a changed handoff disables the fallback until its sockets are reviewed. Asset preparation preserves this authored content.

`src/presentation/shadow-proxies.ts` owns live alpha silhouettes for solid placed sprites, actors and dropped items, plus triangulated authored painting masks at their accepted depths. Casters borrow sprite geometry and textures; they are excluded from beauty and focus passes and released before room resources. `src/presentation/silhouette-pose.ts` supplies the same physical pose to casters and lighting receivers, including authored rotation and mirroring. Scene shadows cover the sun and the five existing illumination slots (hero lantern, three fixtures, transient ability). `src/presentation/local-light-shadows.ts` owns 512-pixel cube depth maps, retires them on room replacement and disables inactive sources. The lighting shader attenuates each source separately; painted mask pixels reconstruct their receiver position from authored depth rather than receiving a flat ground stain. Appearance → Shadow controls solid casting; legacy `contact` values retain contact grounding and now also cast silhouettes, while `none` remains an explicit opt-out.

## Tooling and builds

Node tools use `using`/`await using` with [scope-exit](../tools/scope-exit.ts) for borrowed cleanup contracts; native disposable temporary directories register deletion at acquisition. Scope exit preserves both operation and cleanup failures. [Diagnostic scenarios](../tools/smoke/scenario.ts) own reporting and shutdown through that same boundary.

`tools/cli.ts` owns import-safe command admission and synchronous/asynchronous error reporting. Tool entry points call workflows; workflows call process, asset and file helpers. Helpers do not dispatch npm commands or import their callers. Standard tools run directly. Tests/checks execute fresh; immutable prepared assets cache expensive production work.

AssetWorkspace owns the selected asset root, resolved public/metadata paths, identity and release. Development, web compilation and runtime validation receive those paths explicitly. TypeScript preparation operations receive an explicit context with source access, paths, output recording and one budgeted writer. Atlas compilation requires that context; its pages, calibration, report and manifest use the same writer and budget as other preparation outputs. Source reads share exact-case and root-confinement validation. Environment translation remains at command, Python and legacy diagnostic subprocess boundaries.

Preview sessions own server acquisition, identity checks and lease release once. Game/Authoring profiles select outputs, asset scope and tool navigation together. Live desktop Game uses the Game capability profile against Vite and keeps preview storage; only authoring profiles expose mode switching. Electron resolves preload beside its main bundle in live and packaged launches. Builds pass source and asset identities explicitly to the writer; the standalone identity command verifies existing artifacts. Artifact checks remain independent of compilation. Web inputs exclude Electron-only source, and web identities cover only web output; packaging composes Electron through the shared build configuration and records a desktop identity covering both outputs. Prebuilt packaging requires a matching desktop identity.

## Import boundaries

`npm run architecture:check` protects browser/runtime imports, the pure gameplay model and presentation direction, including type imports and literal dynamic imports. Runtime code uses the Bridge/browser adapter rather than importing Node, Electron, tests or tools. Core cannot import live scenes or art composition. Core runtime imports cannot load asset modules; shared heading rules belong to content, while type-only animation clip contracts remain allowed. ## Change recipes

### Change saved state

Gameplay checkpoint admission belongs to `src/core/save.ts`, with per-area schemas and validation in `src/core/area-state.ts`; settings belong to `src/platform/settings.ts`. `src/platform/bridge.ts` owns the host protocol, while `src/persistence.ts` owns application storage admission, cancellation of waits and checkpoint write feedback. Browser and desktop adapters share `src/platform/storage-codec.ts` for detached write snapshots, payload limits and invalid-data handling. Game entry points select the content registry explicitly when creating adapters; storage never selects production content internally.

Prototype checkpoints use version 9, including the optional permanent `forgeUpgrade` choice in adventure state. Earlier versions return an incompatible empty result and start a fresh run. Within valid version 9 data, omitted enemy Burn timers, local alerts and adventure onboarding history default to absent status, no alerts and empty history. Input queues remain transient; paused and inactive destinations do not advance Burn timers. Settings use version 6; version 5 visual settings migrate with default audio settings. Other invalid or incompatible data loads as empty; transport failures remain visible.

Adapters validate writes; Electron snapshots writes at admission and serializes reads and writes through one queue. A read finishes and closes its file before a later write begins, so loads cannot observe later writes. Failed operations do not poison the queue; mode switching drains admitted work. File replacement remains atomic. Browser and desktop isolate prototype profiles.

Inventory edits use one typed equip, unequip or salvage command through Application and GameSession. InventoryState validates and freezes a private draft once, returning whether it changed; unchanged commands publish no inventory event and submit no checkpoint write.

`InventoryState` owns the permanent forge choice with resource balances in one immutable snapshot. `GameSession.prepareForgePurchase` validates contact and prepares a single-use candidate; Application saves its complete checkpoint before committing it. Purchase admission blocks overlapping inventory/session commands and stale autosaves until the write settles; failed writes accept no spending. Combat rounds hero Physical damage using Edge and initial-hit/over-time Burn damage using Ember once at the damage boundary. Equipment, rest and death do not remove the choice.

Change checkpoint capture/restore and the relevant codec together. Test with `npm test -- tests/unit/persistence.test.ts tests/unit/application.test.ts`. Add migrations when external players create a real compatibility need.

### Add an area or enemy

Author scene geometry and visuals together. For Game, register the area and its resolved visuals in `src/content/game-content.ts`; saving an editor draft alone does not change Game. Extend actor definitions in `src/content/actors.ts` and their art bindings in `src/content/visuals.ts` when needed. Keep simulation independent of art. Check pure transitions, collision and combat, and cover changed browser behavior under [test selection](verification.md#test-selection). Existing development checkpoints can reset when IDs or geometry become incompatible.

### Change action timing or presentation

Input receives the current room's read-only enemy views for body aiming. Its narrow projected humanoid capsule resolves a cursor on a living, unobstructed, same-elevation enemy to that enemy's feet; other cursor positions project onto the walking surface. This supplies an aim point only, without changing simulation reach, damage, attack arcs or action commitment. No target identity survives room replacement.

Authored hero holds, gameplay tuning and simulation own timing at 60 Hz. The hero's melee definition owns base/lunge reach and an optional `sweepRange` override, falling back to base reach; action timing owns the damage window. Sweep defaults to the Quick preset shared by simulation, retimed presentation clips and the effect clock. Preview overrides change no raster assets or persisted fields. [Sweep review](developer-tools.md#sweep-review) owns preset timings and recovery comparisons.

Supplied actor kits use the nearest delivered facing for each action without mirroring. Authored scene placements still require their requested clips and headings.

Run contacts are authored by drawing index and converted to notifies after locomotion retiming. Marked clips use contact-driven footsteps; distance fallback is reserved for unmarked kits. An actor visual can bind a one-based `attackContactDrawing` for supplied attacks without a contact notify. Content validation requires that drawing in every delivered attack facing; presentation maps its onset to the simulation windup boundary while retaining the supplied raster timeline. Animation callbacks never commit damage. Preserve generation-scoped immutable events, fixed-step outcomes and resource disposal. Use action/foundation unit tests, prepared-asset tests for registration changes, and optional native diagnostics for visual investigations.

EventHub captures detached, frozen event batches, including position tuples, before invoking observers. Its bounded history exposes a frozen snapshot; neither publishers nor subscribers can alter queued feedback or history. It delivers gameplay and animation feedback in publication order. Reentrant publication waits behind the current batch; new subscriptions start with the next event, and unsubscribe takes effect immediately. Replacing a generation aborts old subscriber work and stops stale queued or in-flight delivery. Disposal closes the hub permanently. A subscriber exception or current-lifetime promise rejection removes that subscriber, aborts its pending work and reports one diagnostic through Application status without interrupting peers, gameplay, transitions or autosaves. Rejections from aborted lifetimes are discarded; subscribers must use the supplied AbortSignal to cancel their own asynchronous effects.

GamePresentation owns shared CombatFeedback. Its declared combat catalog assets belong to SceneContent's initial requirements and are acquired with each room batch under [SceneAssets ownership](#asset-ownership-and-disposal). Room reset clears active and queued effects before superseded batches release; application disposal closes presentation and its event subscription before asset release. Direct positive damage events queue one Contact Shear at each confirmed target, regardless of attacker kind. Damage outcomes carry Physical/Burn type and direct/over-time phase; Burn ticks retain their persistent cue without replaying contact effects or impact sounds. The sweep effect uses its original pre-painted camera-facing view and fixed registration, scale and timing; it never decides damage or changes the artwork geometry.

### Change player menus or settings

Keep native DOM controls and the shared Application lifecycle. Verify focus return, nested confirmation cancellation, accepted input, pending operations and failure feedback. Settings remain separate from checkpoints; Sandbox cannot write checkpoints. Use application tests and the Game browser scenario.

## Audio

Application owns one `AudioPlayback` and its `AudioFeedback` subscription for Game, Dev Preview and editor playtests. Audio initializes its context and gain graph during startup; playback remains locked until a user gesture resumes that existing context. Effects consume accepted generation-scoped gameplay events; fixed action-contact ticks drive sword/flare sounds, and actual traveled distance drives footsteps for supplied kits without reliable notifies. Audio cannot commit damage, progression, transitions or saves. [Sound design](sound-design.md) owns the palette and cue mapping; [assets](assets.md#audio-preparation) owns cooking and delivery. Music remains deferred.

One-shots recheck generation, abort signal, mute, pause and a 250 ms deadline after loading. Cooldowns begin only after successful playback. `src/audio/voice.ts` owns each source, gain, decoded lease and cancellation subscription through one idempotent completion path. Playback registers every voice, including pending and crossfading ambience, in one resource owner; ambience groups only select fade behavior. Pause, mute and disposal close all sibling resources even when one cleanup fails; disposal also attempts every bus disconnect and context closure. The limit is 24 one-shot voices, reserving four for player-critical feedback; ambience loops are counted separately. Variants avoid immediate repetition; world cues attenuate with distance and are culled at 16 m. Master/effects/ambience settings update live independently of checkpoints. Pause/loading/backgrounding stop world voices and loops; menu feedback remains available. Mute cancels pending work and active voices without a backlog on unmute.

Ambience has one requested destination, up to two layers, and a one-second crossfade. Superseded loads cannot start, failed destination changes preserve outgoing audio, and all retiring loops/timers close on pause, mute or disposal. Near a campfire, its loop replaces one environmental layer. `src/audio/buffers.ts` owns verified decoding, shared pending loads and the decoded-buffer cache. Every consumer claims the buffer before awaiting loading; successful admission transfers that claim into a lease. Preload releases its temporary lease, while playback transfers its lease to the voice through completion. Cue, world, session and ambience lifetimes cancel waiting consumers promptly and release their claims; a surviving borrower preserves shared work. The last pending claim unregisters its entry before aborting transport, so a replacement can enter the acquisition queue immediately. One two-slot DecodeQueue bounds both sample transport and native decoding across preload, one-shots and ambience. Queued cancellation removes work before transport starts. Cancelled active work retains its slot until settlement, preventing repeated retries from exceeding the bound; replacement work waits when both slots remain occupied. Native decodes remain observed through settlement, and obsolete results cannot enter the cache or overwrite a successor. Disposal settles callers without waiting for native work. Pending consumers, active voices and crossfading loops therefore remain counted and cannot be evicted. Unleased entries evict under a 32 MiB cache budget; live leases may exceed it until their owners finish. Application disposal stops voices, closes buffer admission, cancels sample fetches and rejects late decodes before closing the context and releasing assets.

Playback failures are non-fatal, deduplicated and bounded to four diagnostics per application. Unit checks cover lifetime and failure races; browser checks exercise actual decoding and wiring. Neither proves an audible mix. Listen in Game and Dev Preview for balance, overlaps, natural tails and loop seams; Preview provides per-sample audition and stop controls. Published builds require a separately authorized audio asset delivery.
