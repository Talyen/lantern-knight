# Assets

## Ownership

Originals live in the iCloud-backed Asset Library under `Lantern Knight`, organized by subject: Characters, Environments, Props, Items, Effects, Title and Loading, and Guides. Useful exports are browsable beside their Sources; original package bytes and internal paths remain unchanged. Preserve archives, unique revisions, canonical hero references, Clean INK prompts and provenance. The source index records hashes as identity and paths as hints; [source recovery](source-recovery.md) handles moves. Ordinary code/build/CI work does not scan the library.

Git contains code, small recipes and the shared pin. Native source collections, prepared pages/catalogs, captures and logs remain outside Git. The external disk cache defaults to 32 GiB. Set `LANTERN_CACHE_BUDGET_GIB` to change it; active readers remain protected. This disk budget is separate from GPU residency.

## Choose a workflow

| Task                                                                     | Action                                                                                                                 |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| Develop code using accepted artwork                                      | `npm run dev`; pinned assets download as needed.                                                                       |
| Move existing artwork or edit scene geometry                             | Use the [scene editor](developer-tools.md#scene-editor); no asset preparation is needed.                               |
| Refresh known artwork inputs                                             | `npm run assets:prepare -- --ids <asset-id>...`; selected producers and their finalizers refresh locally.              |
| Reconcile additions, replacements, moves or deletions across the library | `npm run assets:prepare`; review [coverage gaps](#library-coverage-policy).                                            |
| Build a Game prototype with local artwork                                | `npm run build -- --local` or `npm run package -- --local`.                                                            |
| Share prepared artwork                                                   | Use [assets:publish or assets:publish-files](#preparation-and-publication) when task-scoped assets are ready to share. |

Local preparation does not change the shared pin. Saving a scene does not register it in Game; follow [Game content registration](architecture.md#add-an-area-or-enemy).

## Local preparation review

Use `npm run assets:prepare` to reconcile and prepare the complete current library with native lossless pages, previews, resolution variants and optimized game copies. The same command cooks game-ready GPU copies for opaque images and keeps alpha-sensitive artwork lossless. Unchanged derivatives are reused. `-- --gpu` remains accepted for existing scripts. `-- --ids <asset-id>...` selects its producer dependencies and affected coverage, lighting and delivery finalizers. Unselected producers come from the verified base and their checked staging receipts. A missing complete base or staging falls back to full preparation. Full preparation rechecks all producer keys and sources even after a scoped refresh. One executor handles full and scoped steps. Successful steps cache immutable outputs and source identities; changed inputs or corrupt outputs rebuild the affected step. Freshness/fidelity belong to preparation, with selected original bytes reverified on reuse.

Preparation needs the external source library, Python image tools and [KTX-Software 4.4.2](#images-for-game-use). Create a checkout-local `.venv`, install OpenCV 5.0.0, NumPy 2.0.2, Pillow 11.3.0 and Ruff 0.16.10, and activate it before preparing assets so `python3` subprocesses use that environment. Pillow matches [asset-test setup](verification.md#test-selection); pure tests, builds and packaging need none of these authoring dependencies. The [foreground-selection models](developer-tools.md#local-foreground-selection-setup) have their own environment and setup command. `--proof` explicitly requests full preparation and a ground contact proof. Preparation never regenerates original artwork.

`assets/recipe.json` owns producer inputs and dependencies. Full and scoped preparation use one dependency graph, rejecting duplicate producers, missing dependencies and cycles before execution. TypeScript steps are callable operations registered in `tools/assets/operations.ts`. They receive an explicit preparation context for source access, paths, atomic output recording and incremental byte accounting. Compiler writes use the same writer. Python subprocesses receive the translated context at their launch boundary; ordinary builds never invoke preparation.

Development prefers its local layer, otherwise the shared pin. Builds and CI use the pin; `npm run build -- --local` and `npm run assets:check -- --local` deliberately inspect a local preparation. No candidate/preview/publication-state protocol is needed to iterate.

A source-verified preparation that reuses another checkout's immutable snapshot still selects that snapshot for the calling checkout's next preview.

## Consumption

Consumers acquire an explicit workspace with its root, identity and release operation. Legacy preparation/test subprocesses receive paths at their process boundary. Missing or corrupt pinned downloads are verified before installation; valid cached assets work offline. Safe extraction, inventory checks, exact bytes and active leases remain required.

### Game and build selection

Builds derive a selected inventory including manifests, pages, registration, lighting/surface companions and loading media. They validate and copy those files once. Vite does not copy the entire public directory before pruning it. Game artifacts select the assets required by resolved Game content, including its initial effects and actors. Published runtime delivery includes those dependencies and the base runtime resources. Game builds acquire selected files from the shared pin, including existing authoring assets newly selected for Game. Individual-file delivery materializes only those references and their companions; older pins use the authenticated archive fallback. Publish new or changed asset bytes when ready to share them within the assigned task; separate approval is not required. Additional authoring resources form separate bundles: authoring requires runtime, while Game/CI can request runtime alone.

Game selection projects registration to its selected asset identities, retaining animation metadata and matching scenery coverage. Its generated policy hashes the projected bytes; development serves the same projection without changing pinned files. Authoring keeps full registration. Game also groups existing lighting images and PNG pages up to 512 KiB into indexed containers, retaining individual-file compatibility. This is byte packaging, not image generation. Container and image hashes remain checked. AssetRuntime's AssetByteSource shares each container download among active readers and caches verified bytes in a 32 MiB LRU. Individual cancelled reads preserve other readers; the last cancelled reader retires and aborts transport so recovery can request that container again. Late results cannot replace the successor or populate the cache. Texture delivery admits at most six active page decodes. The last pooled claim cancels its image request and queued decode; shared claims keep work alive. Active native decodes retain their slot until completion and release cancelled results without upload. Disposal rejects queued work before releasing late textures.

### On-demand authoring

Browser authoring previews use on-demand pinned files or a complete local preparation. Library thumbnails fetch artwork as entries become visible in the scroll panel. Scene saving acquires the manifests it validates; ground selection acquires the source image before invoking its model. Verified files remain cached for offline use. Game builds and CI acquire verified selected files under an active workspace lease. Game development also resolves selected files across the full pin, including artwork in authoring bundles; live authoring desktop development acquires its complete workspace.

A small compressed, hash-pinned catalog maps each file to its own SHA-256, size and exact byte range in an immutable uncompressed container. Files with identical bytes share storage. The editor requests only the selected file's range, with at most four concurrent downloads, and rejects ignored ranges, incorrect offsets, transformed responses, excess bytes and hash mismatches. Container hashes identify the hosted bytes; per-file hashes authenticate each independently downloaded image, manifest or preview. Pins without a file catalog acquire complete verified authoring bundles through the build loader. Use `npm run dev -- --eager` to acquire the complete browser authoring workspace upfront.

### Shared pin and catalog bindings

The shared version 3 pin identifies separate runtime and authoring bundles and an optional individual-file delivery catalog. Existing monolithic releases remain preserved. Exact prepared publication payloads can seed pinned authoring acquisition offline; consumers retain their own hardlinks and leases.

The shared `assets/lock.json` has a 128 KiB repository limit for sharded bundle identities and delivery references. Per-file catalogs and asset payloads remain external; other JSON files retain their existing size limits.

Game content can reference any prepared library ID by its stable manifest path. There is no second promotion allowlist. Authoring catalog overlap is allowed only for an identical binding; a conflicting path still fails. Current combat defaults use Sword Finisher 03 and Blocked Contact Shear from the existing pin without regenerating or publishing original artwork.

## Preparation and publication

Agents may run `assets:publish` and `assets:publish-files` when assets within their assigned task are ready to share, without separate publication approval. Respect explicit user restrictions and preserve unrelated artwork and pins. Inspect new or changed artwork before publication; source verification and delivery validation remain required. `npm run assets:publish` prepares/reuses current source-verified outputs, validates consuming runtime references, publishes immutable runtime/authoring bundles and individual-file delivery, verifies downloadable bytes and atomically changes the pin. Failure preserves the previous pin. Previously hashed remote bundles can reuse a strong HTTP validator: an unchanged response avoids a second full download; new, changed or weakly validated responses receive the complete size and SHA-256 check. It does not package the game, require capture galleries, or claim production-art approval. Publication needs an authenticated `gh` release writer and working download access.

Delivery reserves compression space through the same configurable cache budget. Publication refreshes the complete local layer and stages its source-verified outputs into a candidate inventory. An exact matching candidate retains its checked inventory and hardlinks on retry; changed files or recipes rebuild it. It does not encode the images again or create a monolithic archive. Bundle layout and upload tooling do not belong to the artwork recipe identity; producer and preparation changes still invalidate it. The version 3 outer identity names the candidate inventory; downloadable bundle identities still hash their actual archive bytes. Older pins remain readable. Bundle compression reuses verified file hashes, and interrupted uploads reuse matching checked local archives. New authoring and bootstrap bundles each use 64 stable path-hash shards, subdividing only oversized shards at the 1 GiB payload target (an indivisible larger source file retains its own bundle). Deleting one file cannot shift neighboring shard boundaries. The first publication with this partition scheme replaces the previous monolithic bootstrap bundle; older pins remain readable. Bundle uploads and verification run with three bounded workers. On failure, admission stops and active transfers settle before staging or leases are released. Successful publication removes only its verified staging archives after the pin is accepted, retaining the source preparation and immutable remote releases. Interrupted publication retains checked archives for retry. Active readers remain protected; close unused previews if their leases prevent publication from fitting.

`npm run assets:publish-files` adds individual-file delivery for the already accepted pin, without discovering sources, refreshing preparation or changing artwork. When delivery is missing, it verifies the complete pinned payload, groups unique file hashes into bounded uncompressed containers and publishes them to GitHub Releases. An existing delivery is reverified directly, without acquiring the complete payload or uploading it again. Publication of a new preparation authenticates the previous pin's catalog and reuses immutable container locations by content hash and size, including renamed files and aliases. Only new hashes enter new containers, with two bounded construction/upload workers; removed files disappear from the new catalog. Every retained container receives the host SHA-256 digest and byte-count check, plus a verified nonempty file range when present. Range proofs use the smallest nonempty member of each container and three bounded workers. New catalogs are downloaded and hash-checked before atomically adding `fileDelivery` to the pin. Temporary storage is reserved up to its required peak and reused across stages; container construction and range verification fall back to fewer workers when the cache grants space for only one transfer. A changed pin or failed publication preserves the previous delivery. Retries reuse verified remote containers. No new storage provider is required. Seeding a complete workspace from exact local preparation uses hardlinks while holding the source lease, reserving staging metadata rather than a second copy of the payload; the destination retains its full verification receipt. Original archives remain available for complete build/CI acquisition; editor file selection downloads no surrounding container bytes.

Publication is sharing prepared assets, separate from shipping a game. Original artwork generation/editing follows AGENTS and the art-direction skill. Inspect generated artwork when authoring it; the publisher does not turn aesthetic advice into release receipts.

## Runtime composition boundary

Scene layout, gameplay geometry, camera and lighting are runtime content. Preparation recipes own artwork-producing inputs and dependency order. Moving existing scenery does not bake or publish artwork. Changes to authored hero drawings, timing, registration or bake calibration require affected preparation; runtime timing overrides remain content. Source-free tests still verify the resulting current bindings.

The current TEST hero uses supplied native drawings, eight-direction running, four-direction idle/actions, guarded treatment and rigid-sword protection. Source handoff timing and raster bytes remain preserved; gameplay uses authored 60 Hz holds. The owner-supplied Last Ferry loading video is copied unchanged and played silently during loading. These choices do not establish final art quality.

`authoring/hero-scale.json` owns per-clip and per-drawing registration scale. `authoring/hero-motion.json` owns native-space motion landmarks and is hashed by animation registration. Scale-only preparation changes leave that motion identity intact; publishing newly prepared artwork remains a separate step.

Calibrate hero size against the current idle's head and upper-torso proportions at equal world scale. Use the matching diagonal idle or both neighboring idles for cardinal runs, then inspect every drawing, loop seam and action join. Silhouette height and width include pose compression, weapons and coat tails; they cannot determine anatomical scale. Prefer uniform clip corrections about the native pivot, reserving drawing overrides for confirmed size outliers. Inspect registration drift separately and preserve deliberate bob, lean and airborne poses.

## Cache and retention

`LANTERN_CACHE_ROOT` can choose an external disposable location; `ASSET_LIBRARY_ROOT` selects the parent source library. Temporary download reservations are released after installation. Unused local cache entries are evicted within the budget. `npm run assets:clean` cleans local disposable data only, preserving the current pin and active readers. Published releases and source originals are never deleted by cleanup.

`npm run assets:inspect -- <asset-id>` prints bounded metadata from the shared pin. Use `npm run assets:inspect -- --local <asset-id>` to inspect checkout-local preparation, falling back to the pin when none exists. Inspection acquires an authoring workspace and can download its complete payload on a cold cache; its output is bounded, but it is not an individual-file request. Explicit diagnostics retain output externally; normal checks do not keep passing-evidence receipts.

## Library authoring coverage

The authoring catalog includes delivered townsfolk, wildlife, searchable containers, portal clips and hero interactions. `assets/library-packs.json` supplies adapters for their original metadata contracts; `assets/library-artwork.json` supplies registration for intact paintings and loose artwork. Discovery also covers additional loose files and archive members. These recipes do not restrict library eligibility. `tools/assets/library_import.py` owns ordered metadata alias policies for registration and timing; adapters select those policies without changing source precedence. Source identities and locations remain in the source indices. No file discovery runs in Game, builds or CI.

Use `npm run assets:prepare -- --ids library-all` to refresh this catalog locally. Intact scene paintings are placeable ground panels where registered, with editable provisional world scale. Supplied resolution variants belong in the prepared catalog at their original dimensions. Preview media remains available source material; video scene objects require a media renderer. Existing Game bindings and the published pin do not change.

The authoring catalog includes supplied combat animation kits with their original millisecond timelines, contact markers, fixed pivots and transparent terminal holds. Enemy and hero timing variants remain separate clips. Packs without a delivered world density use the provisional 256 pixels per unit registration; they carry no gameplay collision or damage authority. Loose title artwork and waypoint source sheets are available as reference assets.

## Library coverage policy

The prepared authoring library must represent every distinct supplied asset and version in the current external library. Resolution, concept/study status, review labels, folder names and current Game selection are not eligibility filters. Archives, duplicate exports and provenance may map to the same logical asset; they do not require duplicate scene objects. Keep provenance and distinguish original drawings from upscaled versions without hiding either.

Native originals retain their own bindings even when Game already uses a processed version of the same source. A cropped or resized Game derivative cannot stand in for its master. Identical prepared bytes may share storage.

Preserve supplied image dimensions, pixels, alpha, animation frames and timing. Complete Scenes includes its 6144×4096 paintings. Scale registration with resolution so a higher-resolution variant does not become a larger world object. Atlas packing size is a preparation setting, not an eligibility limit on supplied images. Rendering checks the actual GPU texture limit and reports unsupported use.

Reconcile explicit preparations against the current external library. Recover moves by content identity, remove entries whose sources are absent, and report unregistered assets, unsupported formats and unresolved registration as coverage gaps. Do not classify an unknown archive as rejected, superseded, deferred or source-only from its name. New import adapters must close these gaps; a successful preparation of the registered subset is not proof of complete library coverage.

Cache budgets limit residency and preparation working space, not asset eligibility. Game builds may select the assets they use, and agents choose when to publish task-scoped assets; those delivery choices must not restrict authoring-library availability. Reference-only presentation records a current integration limitation, not permanent exclusion from scene use.

## Images for game use

The original remains authoritative. Preparation retains a full-resolution lossless PNG page and generates a small preview. Complete scene paintings are intact single images: their layout uses clamped UVs, preserves aspect ratio and compensates for ground foreshortening. They do not repeat unless the author explicitly chooses Repeat.

Game delivery adds full-composition approximately 2K, 4K and native variants for intact single-frame images. Actors and animation atlases retain native registration and dimensions. Alpha-sensitive images use lossless PNG delivery, preserving soft edges and additive effects. Ordinary preparation also cooks opaque native images with GPU-compatible block dimensions using UASTC level 1 and Zstandard level 6. Reduced variants remain lossless PNGs. Quality is reviewed on representative assets when the encoder profile changes. Routine preparation checks container dimensions and source/cache identities; it does not decode every compressed image again for pixel comparisons. Compatible RGB and RGBA PNGs retain their original encoded bytes; adding an opaque alpha channel is unnecessary. Color-profile, orientation and format conversions still run when required. Only resized variants and previews need PNG encoding. Originals remain unchanged.

GPU cooking requires Khronos KTX-Software 4.4.2 (`ktx` on PATH or `LANTERN_KTX`). The runtime retains native detail when it fits the actual GPU limit; mipmaps handle minification. Smaller full-composition variants support constrained GPUs. Screen dimensions alone do not establish projected image coverage during camera pan or zoom, so they do not silently downscale assets. It follows the UASTC target preference of ASTC, then BC7; other devices use PNG. Source-quality inspection uses native lossless images. Use representative scene, sprite, effect and UI samples to review a codec profile in the renderer before applying it broadly. Loading and disposal follow asset leases; the whole library is never loaded into GPU memory at once. Mipmaps are sampling levels for reduced display size, not repeating texture behavior.

## Coverage and limitations

Explicit preparation scans loose files and ZIP members by content identity. Duplicate copies share an image binding; distinct resolution versions remain distinct. Moves update locations; a source absent from the active library cannot be recovered from unrelated storage. The finalized catalog removes stale library outputs. Interrupted candidates resume through a checkout-local checkpoint; every reused producer, source identity and derivative hash is revalidated before activation. Preparation verifies image catalog coverage, native media hashes and the source snapshot before activating its local layer.

Metadata adapters interpret animation timing, pivots and slices. Unrecognized or incomplete animation contracts are listed in the prepared inventory with their actual failure, while the supplied images and native media remain available. The editor's Source inventory & media panel exposes coverage counts, source associations, media previews/downloads and these limitations. It does not invent missing timing or convert source sheets into guessed animation. SVG originals and fonts remain downloadable; SVGs can be previewed as images. Video/audio are available media, not yet playable scene objects; GLB/Blend files require a model importer.

Shared content is hardlinked and counted once, free disk space is checked, and active leases cannot be evicted. `LANTERN_PREPARE_BUDGET` overrides the preparation workspace target in bytes (default the cache limit). [Publication](#preparation-and-publication) owns bundle partitioning and pin updates. Browser/device verification is required for actual renderer and codec compatibility.

## Preparation guidance

Preserve frame registration and animation timing when trimming/packing sprites; complete scene paintings stay standalone and never inherit a sprite-atlas page limit. Existing native sheets can be retained as delivered. Further sprite packing should reuse the compiler and prove pixel/registration parity rather than inventing frame fitting.

Use conservative content-based format profiles, and review a representative batch before expensive full-library GPU cooking. Lossless storage compression levels change preparation time and bytes on disk, not decoded image quality. Cache image derivatives by source hash and explicit encoding settings; edits to runtime loading or reporting must not force pixel encoding again. Ordinary builds consume prepared artifacts and never cook source artwork implicitly.

Transparency classification reads only alpha values; it does not calculate full-image sharpness, entropy or dominant colors. Preparation carries verified file hashes between stages, hashes shared inodes once per checksum pass, and batches metadata reads. Reused producers link existing immutable bytes and do not repeat cache growth reservations; new outputs and the final layer still receive full budget accounting. Resume copies only missing completed step caches.

The atomic writer hashes output buffers once and records the installed file identity. Later stages reuse that proof while file metadata matches; changed or unknown files are hashed again. Native library import and delivery check source identity, dimensions, manifests and coverage during generation instead of regenerating the same outputs for verification. Detected output changes fail before activation. Encoding fingerprints track producers, encoding inputs and settings; filesystem orchestration remains a workflow input without invalidating every pixel producer.

Primary guidance: [Khronos KTX Artist Guide](https://github.com/KhronosGroup/3D-Formats-Guidelines/blob/main/KTXArtistGuide.md), [KTX encoder presets](https://github.khronos.org/KTX-Software/ktxtools/ktx_create.html), [NVIDIA asset compression workflow](https://developer.nvidia.com/astc-texture-compression-for-game-assets), and [Unreal derived data caching](https://dev.epicgames.com/documentation/unreal-engine/using-derived-data-cache-in-unreal-engine). These inform the workflow; project-specific quality requirements still need actual scene/device validation.

## Frequent artwork changes

Use `npm run assets:prepare` after adding, replacing, moving or deleting artwork. One command updates the catalog and optimized game copies. Running previews keep their current immutable snapshot; reopen them after a refresh when ready, preserving unsaved scene work first.

Discovery reuses hashes and image metadata for unchanged files. For changed archives, unchanged members reuse their decoded metadata by content hash. Native pages, placement masks, lighting companions and image delivery are reused individually. A small artwork edit does not regenerate unrelated images or their companions. Interrupted refreshes retain verified base files when their inode, size and modification time still match; partially changed files are checked normally. Successful activation retains the completed verification proof for the next refresh, avoiding another full read of the library. New files receive normal bindings, and deletions remove stale catalog entries. Preserve the [importer identity metadata](source-recovery.md#importer-metadata) so replacements and moves retain scene references.

Preparation runs below normal process priority. Encoding is limited by both job count and measured working memory; large images cannot start an unbounded group of encoders. The normal path uses the reviewed faster UASTC profile for native game copies, retains existing higher-quality cooked copies, and preserves lossless originals. Reduced lossless PNGs cover smaller device texture limits; new edits do not cook unused intermediate GPU tiers. Full visual/decoded-image comparisons belong to profile qualification, not every refresh.

Local layers share native public images and media, retaining small producer receipts, manifests and required staging inputs separately. Delivery can update manifests without invalidating the original producer documents. Complete verified layers can seed preparation in another checkout without re-downloading the authoring library; ordinary preview selection stays checkout-local. Activation prunes stale files in place and atomically changes the pointer; it does not reconstruct another complete payload. Quota reservations follow newly allocated bytes with exponentially growing credit. Each accounting pass grants only available cache and disk headroom, including a bounded final grant near the limit; it never retries a rounded reservation for each output. Final activation checks actual residency. The checkpoint index remains leased until activation, so eviction cannot discard recovery state mid-refresh. Older unused layers for the same checkout are removed; active readers and other checkouts remain protected.

Preparation resolves original archive members through their content hashes. Identical loose files inside the active source library are preferred; original text/JSON metadata is retained byte-for-byte under `.lantern/metadata/`. Discovery retains member hashes, native PNG dimensions and filesystem proofs in `.lantern/identities.json`, so clearing disposable caches does not require unchanged ZIPs to be downloaded again. ZIPs remain preserved originals and supply uncaptured or unavailable members. Existing producer receipts cache normalized metadata and outputs by source inventory and importer inputs; changed inputs invalidate the affected producers. Retained metadata never adds a deleted archive back to the reconciled library.

Preparation reports source reconciliation time, per-step elapsed time, producer reuse and image encode/reuse counts. Compare changed-input runs with equivalent sources and cache state; unchanged source-verified reuse is a separate measurement. The few-minute iteration target concerns routine changes with a complete local layer and sufficient cache space. A cold import, a new encoder profile, missing derivatives, or publication network transfers can take longer. Raise `LANTERN_CACHE_BUDGET_GIB` beyond the default when complete preparation and active authoring outputs need more room; budgets do not exclude source assets or evict active readers.

Library metadata import reuses discovery's local hash proofs only while device, inode, size and nanosecond modification/change times match. Modified or moved sources return to content verification. It reports the archive or metadata being opened and stops after ten minutes without subprocess output, rather than imposing a two-minute deadline on the entire library. Failure retains the last import progress in the error. Discovery and source resolution reject macOS cloud placeholders before reading their contents; use Download Now in Finder and retry after the named file finishes downloading. Failed preparation preserves the active layer and shared pin.

## Audio preparation

`assets/audio-sources.json` selects stable sample/cue IDs, exact source hashes, segments and gain offsets from the sibling `Sounds` library. `LANTERN_SOUND_LIBRARY` overrides that authoring-only root. `npm run assets:audio-review` exhaustively classifies every filename into selected, alternate, future-use, unsuitable or unclear, with suggested use and rationale; non-audio files are accounted separately. Reports go to the external audio-review cache, never Git. This filename review does not claim auditory approval or infer licenses from filenames.

`npm run assets:prepare -- --ids audio` cooks only the selected sounds over a verified prepared base, without requiring image staging. Full preparation includes the same producer. FFmpeg/FFprobe 9.x are authoring dependencies (`LANTERN_FFMPEG` / `LANTERN_FFPROBE` override executables); exact tool fingerprints participate in preparation keys. Every invocation, including reuse, verifies selected source bytes against their recipes. Ordinary builds never require these executables or the source library.

One-shots are mono 44.1 kHz, 16-bit PCM WAV. Ambience is stereo 48 kHz Vorbis at 128 kbps using FFmpeg 9's native encoder. Preparation measures mean/peak levels, limits normalization boosts to 18 dB, applies authored family gain, and limits peaks. One-shots remove leading silence below -55 dB; recipe segments and short terminal fades bound duration. Loops bake a 250 ms equal-power wrap seam and record decoded loop bounds. Originals are preserved.

The separate typed `audio/manifest.json` records IDs, relative content-addressed paths, hashes, sizes, durations, channels, sample rates and loop boundaries. Source/processing receipts stay in external metadata. Identical cooked bytes share files. Runtime selection, bundle publication and asset checks include all selected audio and verify hashes; no runtime path points at Documents. Local prototypes use prepared layers. Local preparation leaves the pin unchanged; agents may publish task-scoped audio when ready under [preparation and publication](#preparation-and-publication). Pins without an audio manifest build and preview silently. Present manifests and their samples still require schema and integrity validation.
