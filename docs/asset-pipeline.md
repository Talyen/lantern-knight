# Asset pipeline internals

Implementation contracts for asset-tool changes and delivery/cache diagnosis. For preparing, inspecting and sharing artwork, use the [asset workflow](assets.md).

## Preparation

Use `npm run assets:prepare` to reconcile and prepare the complete current library with native lossless pages, previews, resolution variants and optimized game copies. The same command cooks game-ready GPU copies for opaque images and keeps alpha-sensitive artwork lossless. Unchanged derivatives are reused. `-- --gpu` remains accepted for existing scripts. `-- --ids <asset-id>...` selects its producer dependencies and affected coverage, lighting and delivery finalizers. Unselected producers come from the verified base and their checked staging receipts. A missing complete base or staging falls back to full preparation. Full preparation rechecks all producer keys and sources even after a scoped refresh. One executor handles full and scoped steps. Successful steps cache immutable outputs and source identities; changed inputs or corrupt outputs rebuild the affected step. Cached file restoration and verified output registration use bounded batches; a failed batch drains admitted filesystem work before releasing its lease. Registration accounts for hardlinks and records verified hashes in the same pass. Freshness/fidelity belong to preparation, with selected original bytes reverified on reuse.

`assets/recipe.json` owns producer inputs and dependencies. Full and scoped preparation use one dependency graph, rejecting duplicate producers, missing dependencies and cycles before execution. TypeScript steps are callable operations registered in `tools/assets/operations.ts`. They receive an explicit preparation context for source access, paths, atomic output recording and incremental byte accounting. Compiler writes use the same writer. Python subprocesses receive the translated context at their launch boundary; ordinary builds never invoke preparation.

## Consumption

Consumers acquire an explicit workspace with its root, identity and release operation. Legacy preparation/test subprocesses receive paths at their process boundary. Missing or corrupt pinned downloads are verified before installation; valid cached assets work offline. Safe extraction, inventory checks, exact bytes and active leases remain required.

### Game and build selection

Builds derive a selected inventory including manifests, pages, registration, lighting/surface companions and loading media. They validate and copy those files once. Vite does not copy the entire public directory before pruning it. Game artifacts select the assets required by resolved Game content, including its initial effects and actors. Published runtime delivery includes those dependencies and the base runtime resources. Game builds acquire selected files from the shared pin, including existing authoring assets newly selected for Game. Individual-file delivery materializes only those references and their companions; older pins use the authenticated archive fallback. Publish new or changed asset bytes when ready to share them within the assigned task; separate approval is not required. Runtime selection never changes immutable delivery membership; Game/CI acquires only its resolved files.

Game selection projects registration to its selected asset identities, retaining animation metadata and matching scenery coverage. Its generated policy hashes the projected bytes; development serves the same projection without changing pinned files. Authoring keeps full registration. Game also groups existing lighting images and PNG pages up to 512 KiB into indexed containers, retaining individual-file compatibility. This is byte packaging, not image generation. Container and image hashes remain checked. AssetRuntime's AssetByteSource shares each container download among active readers and caches verified bytes in a 32 MiB LRU. Individual cancelled reads preserve other readers; the last cancelled reader retires and aborts transport so recovery can request that container again. Late results cannot replace the successor or populate the cache. Texture delivery admits at most six active page decodes. The last pooled claim cancels its image request and queued decode; shared claims keep work alive. Active native decodes retain their slot until completion and release cancelled results without upload. Disposal rejects queued work before releasing late textures.

### On-demand authoring

Browser authoring previews acquire requested files from the shared pin or the selected local preparation. Local demand readers verify each requested file against its preparation descriptor, coalesce concurrent requests and drain reads before releasing their lease. Full checks and preparation still validate the complete layer. Library thumbnails fetch artwork as entries become visible in the scroll panel. Scene saving acquires the manifests it validates; ground selection acquires the source image before invoking its model. Verified files remain cached for offline use. Game builds and CI acquire verified selected files under an active workspace lease. Game development also resolves selected files across the full pin, including artwork previously used only in authoring; live authoring desktop development acquires its complete workspace.

A small compressed, hash-pinned catalog maps each file to its own SHA-256, size and exact byte range in an immutable uncompressed container. Files with identical bytes share storage. The editor requests only the selected file's range, with at most four concurrent downloads, and rejects ignored ranges, incorrect offsets, transformed responses, excess bytes and hash mismatches. Container hashes identify the hosted bytes; per-file hashes authenticate each independently downloaded image, manifest or preview. Pins without a file catalog acquire complete verified authoring bundles through the build loader. Use `npm run dev -- --eager` to acquire the complete browser authoring workspace upfront; version 4 complete acquisition reads each needed container once.

### Shared pin and catalog bindings

The shared version 4 pin identifies the accepted payload and a required individual-file delivery catalog. New publications create no runtime or authoring archives. Version 1–3 pins and their original releases remain readable. Exact prepared publication payloads and validated complete authoring assemblies can seed pinned acquisition offline; consumers retain their own hardlinks and leases.

The shared `assets/lock.json` has a 128 KiB repository limit for sharded bundle identities and delivery references. Per-file catalogs and asset payloads remain external; other JSON files retain their existing size limits.

Game content can reference any prepared library ID by its stable manifest path. There is no second promotion allowlist. Authoring catalog overlap is allowed only for an identical binding; a conflicting path still fails. Current combat defaults use Sword Finisher 03 and Blocked Contact Shear from the existing pin without regenerating or publishing original artwork.


## Publication

`npm run assets:publish` prepares/reuses current source-verified outputs, validates consuming runtime references, publishes changed file hashes and a small compressed catalog, verifies downloadable bytes and atomically changes the version 4 pin. Failure preserves the previous pin. Publication needs an authenticated `gh` release writer and working download access.

Publication stages source-verified outputs into a candidate inventory. An exact matching candidate retains its checked inventory and hardlinks on retry; changed files or recipes rebuild it. Delivery layout and upload tools do not belong to artwork recipe identity; producer and preparation changes still invalidate it. New publication neither encodes images again nor compresses archives. A density-only calibration changes the affected manifest and catalog; unchanged image hashes retain their existing container and offset. Runtime-reference changes require no asset publication when their bytes already exist in the pin.

The publisher authenticates the previous catalog and reuses immutable locations by file hash and size, including renamed files and aliases. Only new hashes enter new containers; removed files disappear from the next catalog. New JSON/metadata containers are separate from image/media containers. Existing mixed containers remain reusable without migration. Hash-prefix partitions bound new containers independently of runtime selection. Construction/upload uses up to two workers, falling back to one when cache headroom is limited. Every retained container receives the host SHA-256 digest and byte-count check, plus its smallest nonempty member's verified range. Range proofs use up to three workers. New catalogs are downloaded and hash-checked before acceptance. Failed work settles active transfers before releasing staging and leases; retries reuse checked remote containers.

`npm run assets:publish-files` upgrades an already accepted version 3 pin to version 4 without discovering sources, refreshing preparation or changing artwork. Existing individual delivery is reverified directly, with no image acquisition or upload. When delivery is missing, it first verifies the complete older payload and creates its file containers. The payload identity, accepted recipe and source provenance remain unchanged by this delivery upgrade.

Demand readers first hash-check matching files in the complete local authoring cache and hardlink them under a retained source lease. Corrupt or absent local files use exact authenticated ranges. The destination records its linked inodes before releasing the source lease. Cold complete authoring acquisition downloads each required container once, verifies its complete hash and each extracted file, and shares aliases through hardlinks. Temporary container bytes and installed objects receive cache reservations; cancellation aborts transport and drains admitted work before releasing the lease. A valid complete workspace works offline. Complete file workspaces retain a verification receipt bound to their authenticated payload and every member's device, inode, size, modification/change times and mode. Reopening unchanged bytes checks these signatures instead of hashing the library again. Missing or modified members return to authenticated verification and repair; shared inodes reuse hashes only after a stable read. Exact local preparation can seed acquisition with hardlinks under its source lease, reserving staging metadata instead of a second payload copy. Legacy archive readers retain safe extraction and full integrity checks.

Cache accounting stores compressed per-entry inode inventories outside payloads. Unchanged inactive entries reuse their inventories across processes; read leases update recency through their lease directory without rewriting or opening the payload inventory. Budget operations load or rebuild the inventory when needed; mutable leases and abandoned writers refresh filesystem accounting. Reserving growth escalates a read lease to a writer and invalidates its inventory. Writers close after admitted writes settle, refreshing only their entry. Missing, corrupt or replaced inventory records rebuild safely. Inventories and lease control files count toward the cache budget. Eviction decrements inode references from the admitted inventory, so shared hardlinks remain counted without another full cache scan after each deletion. Existing caches need an initial inventory pass; active legacy writers still require filesystem scans.

## Image encoding

The original remains authoritative. Preparation retains a full-resolution lossless PNG page and generates a small preview. Complete scene paintings are intact single images: their layout uses clamped UVs, preserves aspect ratio and compensates for ground foreshortening. They do not repeat unless the author explicitly chooses Repeat.

Game delivery adds full-composition approximately 2K, 4K and native variants for intact single-frame images. Actors and animation atlases retain native registration and dimensions. Alpha-sensitive images use lossless PNG delivery, preserving soft edges and additive effects. Ordinary preparation also cooks opaque native images with GPU-compatible block dimensions using UASTC level 1 and Zstandard level 6. Reduced variants remain lossless PNGs. Quality is reviewed on representative assets when the encoder profile changes. Routine preparation checks container dimensions and source/cache identities; it does not decode every compressed image again for pixel comparisons. Compatible RGB and RGBA PNGs retain their original encoded bytes; adding an opaque alpha channel is unnecessary. Color-profile, orientation and format conversions still run when required. Only resized variants and previews need PNG encoding. Originals remain unchanged.

GPU cooking requires Khronos KTX-Software 4.4.2 (`ktx` on PATH or `LANTERN_KTX`). The runtime retains native detail when it fits the actual GPU limit; mipmaps handle minification. Smaller full-composition variants support constrained GPUs. Screen dimensions alone do not establish projected image coverage during camera pan or zoom, so they do not silently downscale assets. It follows the UASTC target preference of ASTC, then BC7; other devices use PNG. Source-quality inspection uses native lossless images. Use representative scene, sprite, effect and UI samples to review a codec profile in the renderer before applying it broadly. Loading and disposal follow asset leases; the whole library is never loaded into GPU memory at once. Mipmaps are sampling levels for reduced display size, not repeating texture behavior.

## Incremental preparation

Preserve frame registration and animation timing when trimming/packing sprites; complete scene paintings stay standalone and never inherit a sprite-atlas page limit. Existing native sheets can be retained as delivered. Further sprite packing should reuse the compiler and prove pixel/registration parity rather than inventing frame fitting.

Use conservative content-based format profiles, and review a representative batch before expensive full-library GPU cooking. Lossless storage compression levels change preparation time and bytes on disk, not decoded image quality. Cache image derivatives by source hash and explicit encoding settings; edits to runtime loading or reporting must not force pixel encoding again. Ordinary builds consume prepared artifacts and never cook source artwork implicitly.

Transparency classification reads only alpha values; it does not calculate full-image sharpness, entropy or dominant colors. Preparation carries verified file hashes between stages, hashes shared inodes once per checksum pass with at most sixteen concurrent streams, preserves sorted output identity, and batches metadata reads. Reused producers link existing immutable bytes and do not repeat cache growth reservations; new outputs and the final layer still receive full budget accounting. Resume copies only missing completed step caches.

The atomic writer hashes output buffers once and records the installed file identity. Later stages reuse that proof while file metadata matches; changed or unknown files are hashed again. Native library import and delivery check source identity, dimensions, manifests and coverage during generation instead of regenerating the same outputs for verification. Detected output changes fail before activation. Encoding fingerprints track producers, encoding inputs and settings; filesystem orchestration remains a workflow input without invalidating every pixel producer.

Primary guidance: [Khronos KTX Artist Guide](https://github.com/KhronosGroup/3D-Formats-Guidelines/blob/main/KTXArtistGuide.md), [KTX encoder presets](https://github.khronos.org/KTX-Software/ktxtools/ktx_create.html), [NVIDIA asset compression workflow](https://developer.nvidia.com/astc-texture-compression-for-game-assets), and [Unreal derived data caching](https://dev.epicgames.com/documentation/unreal-engine/using-derived-data-cache-in-unreal-engine). These inform the workflow; project-specific quality requirements still need actual scene/device validation.

Discovery reuses hashes and image metadata for unchanged files. For changed archives, unchanged members reuse their decoded metadata by content hash. Native pages, placement masks, lighting companions and image delivery are reused individually. A small artwork edit does not regenerate unrelated images or their companions. Interrupted refreshes retain verified base files when their inode, size and modification time still match; partially changed files are checked normally. Successful activation retains the completed verification proof for the next refresh, avoiding another full read of the library. New files receive normal bindings, and deletions remove stale catalog entries. Preserve the [importer identity metadata](source-recovery.md#importer-metadata) so replacements and moves retain scene references.

Preparation runs below normal process priority. Encoding is limited by both job count and measured working memory; large images cannot start an unbounded group of encoders. The normal path uses the reviewed faster UASTC profile for native game copies, retains existing higher-quality cooked copies, and preserves lossless originals. Reduced lossless PNGs cover smaller device texture limits; new edits do not cook unused intermediate GPU tiers. Full visual/decoded-image comparisons belong to profile qualification, not every refresh.

Local layers share native public images and media, retaining small producer receipts, manifests and required staging inputs separately. Delivery can update manifests without invalidating the original producer documents. Complete verified layers can seed preparation in another checkout without re-downloading the authoring library; ordinary preview selection stays checkout-local. Activation prunes stale files in place and atomically changes the pointer; it does not reconstruct another complete payload. Quota reservations follow newly allocated bytes with exponentially growing credit. Each accounting pass grants only available cache and disk headroom, including a bounded final grant near the limit; it never retries a rounded reservation for each output. Final activation checks actual residency. The checkpoint index remains leased until activation, so eviction cannot discard recovery state mid-refresh. Older unused layers for the same checkout are removed; active readers and other checkouts remain protected.

Preparation resolves original archive members through their content hashes. Identical loose files inside the active source library are preferred; original text/JSON metadata is retained byte-for-byte under `.lantern/metadata/`. Discovery retains member hashes, native PNG dimensions and filesystem proofs in `.lantern/identities.json`, so clearing disposable caches does not require unchanged ZIPs to be downloaded again. ZIPs remain preserved originals and supply uncaptured or unavailable members. Existing producer receipts cache normalized metadata and outputs by source inventory and importer inputs; changed inputs invalidate the affected producers. Retained metadata never adds a deleted archive back to the reconciled library.

Cached image delivery validates up to sixteen page receipts concurrently, independently of the encoder queue. Encodes retain their configured worker and pixel-memory limits. Missing receipt candidates use the writer's existing file inventory, while retained receipts still verify their source identity and derivative hashes. Preparation reports source reconciliation time, per-step elapsed time, producer reuse and image encode/reuse counts. Compare changed-input runs with equivalent sources and cache state; unchanged source-verified reuse is a separate measurement. The few-minute iteration target concerns routine changes with a complete local layer and sufficient cache space. A cold import, a new encoder profile, missing derivatives, or publication network transfers can take longer. Raise `LANTERN_CACHE_BUDGET_GIB` beyond the default when complete preparation and active authoring outputs need more room; budgets do not exclude source assets or evict active readers.

Library metadata import reuses discovery's local hash proofs only while device, inode, size and nanosecond modification/change times match. Modified or moved sources return to content verification. It reports the archive or metadata being opened and stops after ten minutes without subprocess output, rather than imposing a two-minute deadline on the entire library. Failure retains the last import progress in the error. Discovery and source resolution reject macOS cloud placeholders before reading their contents; use Download Now in Finder and retry after the named file finishes downloading. Failed preparation preserves the active layer and shared pin.

## Audio encoding

One-shots are mono 44.1 kHz, 16-bit PCM WAV. Ambience is stereo 48 kHz Vorbis at 128 kbps using FFmpeg 9's native encoder. Preparation measures mean/peak levels, limits normalization boosts to 18 dB, applies authored family gain, and limits peaks. One-shots remove leading silence below -55 dB; recipe segments and short terminal fades bound duration. Loops bake a 250 ms equal-power wrap seam and record decoded loop bounds. Originals are preserved.

The separate typed `audio/manifest.json` records IDs, relative content-addressed paths, hashes, sizes, durations, channels, sample rates and loop boundaries. Source/processing receipts stay in external metadata. Identical cooked bytes share files. Runtime selection, bundle publication and asset checks include all selected audio and verify hashes; no runtime path points at Documents. Local prototypes use prepared layers. Local preparation leaves the pin unchanged; agents may publish task-scoped audio when ready under [preparation and publication](assets.md#preparation-and-publication). Pins without an audio manifest build and preview silently. Present manifests and their samples still require schema and integrity validation.
