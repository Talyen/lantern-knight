# Asset pipeline internals

Implementation contracts for asset-tool changes and delivery/cache diagnosis. For preparing, inspecting and sharing artwork, use the [asset workflow](assets.md).

## Preparation

Use `npm run assets:prepare` to reconcile owned sources and prepare the retained scene/Game/authoring selection with native lossless pages, previews, resolution variants and optimized game copies. The same command cooks game-ready GPU copies for opaque images and keeps alpha-sensitive artwork lossless. Unchanged derivatives are reused. `-- --gpu` remains accepted for existing scripts. `-- --ids <asset-id>...` selects its producer dependencies and affected coverage, lighting and delivery finalizers. Unselected producers come from the verified base and their checked staging receipts. A missing complete base or staging falls back to full preparation. Full preparation rechecks all producer keys and sources even after a scoped refresh. One executor handles full and scoped steps. Successful steps cache immutable outputs and source identities; changed inputs or corrupt outputs rebuild the affected step. Cached file restoration and verified output registration use bounded batches; a failed batch drains admitted filesystem work before releasing its lease. Registration accounts for hardlinks and records verified hashes in the same pass. Freshness/fidelity belong to preparation, with selected original bytes reverified on reuse.

`assets/recipe.json` owns producer inputs and dependencies. Full and scoped preparation use one dependency graph, rejecting duplicate producers, missing dependencies and cycles before execution. TypeScript steps are callable operations registered in `tools/assets/operations.ts`. They receive an explicit preparation context for source access, paths, atomic output recording and incremental byte accounting. Compiler writes use the same writer. Python subprocesses receive the translated context at their launch boundary; ordinary builds never invoke preparation.

## Consumption

Version 5 pins select a repository-owned snapshot. `asset-data/inventories/<sha256>.json.gz` contains the exact prepared file inventory; `asset-data/objects/<prefix>/<sha256>` holds unique bytes. The pin checks inventory bytes, recipe identity and the complete payload digest. Objects are authenticated by hash and size before admission. Aliases share a Git blob without losing their logical manifest paths.

Consumers acquire an explicit workspace with public/metadata directories, identity and release. Requested files are copied into ignored `.cache/repository-assets/<identity>/` with filesystem cloning when available and ordinary copying otherwise. Copies remain independent: editing a disposable assembly cannot mutate repository objects. Corrupt assemblies are repaired from owned bytes; missing or corrupt owned objects fail without remote fallback. Release closes admission and drains pending copies. A complete retained workspace is assembled for full checks and eager authoring; Game builds select only their resolved references.

Game selection preserves existing registration projection, lighting/surface companions, containers, image variants and runtime leases. This migration changes byte ownership and acquisition, not raster encoding, frame timing or runtime composition. The renderer's asset pool, image decode limits, memory budgets and disposal rules remain unchanged.

Historical version 1–4 archive/range readers remain for migration and compatibility tests. Current development, build, packaging and CI paths use the repository pin and never download asset bytes from releases.

## Publication

Acceptance verifies all unique prepared bytes, copies them into owned objects, writes a hash-named immutable inventory, then atomically replaces `assets/lock.json`. Existing inventories and objects remain intact, allowing in-flight readers and earlier Git revisions to retain their own snapshot. A changed pin during acceptance aborts rather than overwriting another result. Interrupted acceptance can leave unreferenced objects; it does not activate an incomplete snapshot.

`assets:prepare` and the compatibility `assets:publish` command accept output locally. Git commits carry the source tree, recipes, prepared objects and pin together. Remote release publication is not part of this workflow. `assets:import` copies explicitly named files or folders into owned sources under the preparation lane, verifies bytes, rejects destination conflicts and removes only its newly installed files if a batch fails. Documents reorganization cannot alter owned membership.

Preparation caches remain disposable and budgeted under active leases. They accelerate encoding but supply no unique source authority. Accepted payloads and the source packages needed to reprocess the retained selection are present in Git. Unused external artwork is neither discovered nor prepared. No cache cleanup deletes `asset-data/`.

## Image encoding

The original remains authoritative. Preparation retains a full-resolution lossless PNG page and generates a small preview. Complete scene paintings are intact single images: their layout uses clamped UVs, preserves aspect ratio and compensates for ground foreshortening. They do not repeat unless the author explicitly chooses Repeat.

Game delivery adds full-composition approximately 2K, 4K and native variants for intact single-frame images. Actors and animation atlases retain native registration and dimensions. Alpha-sensitive images use lossless PNG delivery, preserving soft edges and additive effects. Ordinary preparation also cooks opaque native images with GPU-compatible block dimensions using UASTC level 1 and Zstandard level 6. Reduced variants remain lossless PNGs. Quality is reviewed on representative assets when the encoder profile changes. Routine preparation checks container dimensions and source/cache identities; it does not decode every compressed image again for pixel comparisons. Compatible RGB and RGBA PNGs retain their original encoded bytes; adding an opaque alpha channel is unnecessary. Color-profile, orientation and format conversions still run when required. Only resized variants and previews need PNG encoding. Originals remain unchanged.

GPU cooking requires Khronos KTX-Software 4.4.2 (`ktx` on PATH or `LANTERN_KTX`). The runtime retains native detail when it fits the actual GPU limit; mipmaps handle minification. Smaller full-composition variants support constrained GPUs. Screen dimensions alone do not establish projected image coverage during camera pan or zoom, so they do not silently downscale assets. It follows the UASTC target preference of ASTC, then BC7; other devices use PNG. Source-quality inspection uses native lossless images. Use representative scene, sprite, effect and UI samples to review a codec profile in the renderer before applying it broadly. Loading and disposal follow asset leases; the whole library is never loaded into GPU memory at once. Mipmaps are sampling levels for reduced display size, not repeating texture behavior.

## Incremental preparation

Preserve frame registration and animation timing when trimming/packing sprites; complete scene paintings stay standalone and never inherit a sprite-atlas page limit. Existing native sheets can be retained as delivered. Further sprite packing should reuse the compiler and prove pixel/registration parity rather than inventing frame fitting.

Use conservative content-based format profiles, and review a representative batch before expensive full-library GPU cooking. Lossless storage compression levels change preparation time and bytes on disk, not decoded image quality. Cache image derivatives by source hash and explicit encoding settings; edits to runtime loading or reporting must not force pixel encoding again. Ordinary builds consume prepared artifacts and never cook source artwork implicitly.

Transparency classification reads only alpha values; it does not calculate full-image sharpness, entropy or dominant colors. Preparation carries verified file hashes between stages, hashes shared inodes once per checksum pass with at most sixteen concurrent streams, preserves sorted output identity, and batches metadata reads. Reused producers link existing immutable bytes and do not repeat cache growth reservations; new outputs and the final layer still receive full budget accounting. Resume copies only missing completed step caches.

The atomic writer hashes output buffers once and records the installed file identity. Later stages reuse that proof while file metadata matches; changed or unknown files are hashed again. Native library import and delivery check source identity, dimensions, manifests and coverage during generation instead of regenerating the same outputs for verification. Detected output changes fail before activation. Encoding fingerprints track producers, encoding inputs and settings; filesystem orchestration remains a workflow input without invalidating every pixel producer.

Primary guidance: [Khronos KTX Artist Guide](https://github.com/KhronosGroup/3D-Formats-Guidelines/blob/main/KTXArtistGuide.md), [KTX encoder presets](https://github.khronos.org/KTX-Software/ktxtools/ktx_create.html), [NVIDIA asset compression workflow](https://developer.nvidia.com/astc-texture-compression-for-game-assets), and [Unreal derived data caching](https://dev.epicgames.com/documentation/unreal-engine/using-derived-data-cache-in-unreal-engine). These inform the workflow; project-specific quality requirements still need actual scene/device validation.

Discovery reuses hashes and image metadata for unchanged files. For changed archives, unchanged members reuse their decoded metadata by content hash. Native pages, placement masks, lighting companions and image delivery are reused individually. A small artwork edit does not regenerate unrelated images or their companions. Interrupted refreshes retain verified base files when their inode, size and modification time still match; partially changed files are checked normally. Successful activation retains the completed verification proof for the next refresh, avoiding another full read of the library. New files receive normal bindings, and deletions remove stale catalog entries. Preserve the [importer identity metadata](source-recovery.md#importer-metadata) so replacements and moves retain scene references.

Preparation runs below normal process priority. Encoding is limited by both job count and measured working memory; large images cannot start an unbounded group of encoders. The normal path uses the reviewed faster UASTC profile for native game copies, retains existing higher-quality cooked copies, and preserves lossless originals. Reduced lossless PNGs cover smaller device texture limits; new edits do not cook unused intermediate GPU tiers. Full visual/decoded-image comparisons belong to profile qualification, not every refresh.

Local layers share native public images and media, retaining small producer receipts, manifests and required staging inputs separately. Delivery can update manifests without invalidating the original producer documents. Complete verified layers can seed preparation in another checkout without re-downloading the authoring library; ordinary preview selection stays checkout-local. Activation prunes stale files in place and atomically changes the pointer; it does not reconstruct another complete payload. Quota reservations follow newly allocated bytes with exponentially growing credit. Each accounting pass grants only available cache and disk headroom, including a bounded final grant near the limit; it never retries a rounded reservation for each output. Final activation checks actual residency. The checkpoint index remains leased until activation, so eviction cannot discard recovery state mid-refresh. Older unused layers for the same checkout are removed; active readers and other checkouts remain protected.

Preparation resolves original archive members through their content hashes. Identical loose files inside the active source library are preferred; original text/JSON metadata is retained byte-for-byte under `.lantern/metadata/`. Discovery retains member hashes, native PNG dimensions and filesystem proofs in `.lantern/identities.json`, so clearing disposable caches does not require unchanged ZIPs to be downloaded again. ZIPs remain preserved originals and supply uncaptured or unavailable members. Existing producer receipts cache normalized metadata and outputs by source inventory and importer inputs; changed inputs invalidate the affected producers. Retained metadata never adds a deleted archive back to the reconciled library.

Cached image delivery validates up to sixteen page receipts concurrently, independently of the encoder queue. Encodes retain their configured worker and pixel-memory limits. Missing receipt candidates use the writer's existing file inventory, while retained receipts still verify their source identity and derivative hashes. Preparation reports source reconciliation time, per-step elapsed time, producer reuse and image encode/reuse counts. Compare changed-input runs with equivalent sources and cache state; unchanged source-verified reuse is a separate measurement. The few-minute iteration target concerns routine changes with a complete local layer and sufficient cache space. A cold import, a new encoder profile, missing derivatives, or publication network transfers can take longer. Raise `LANTERN_CACHE_BUDGET_GIB` beyond the default when complete preparation and active authoring outputs need more room; budgets do not exclude source assets or evict active readers.

Library metadata import reuses discovery's local hash proofs only while device, inode, size and nanosecond modification/change times match. Modified or moved sources return to content verification. It reports the archive or metadata being opened and stops after ten minutes without subprocess output, rather than imposing a two-minute deadline on the entire library. Failure retains the last import progress in the error. Discovery and source resolution reject macOS cloud placeholders before reading their contents; use Download Now in Finder and retry after the named file finishes downloading. Failed preparation preserves the active layer and repository pin.

## Audio encoding

One-shots are mono 44.1 kHz, 16-bit PCM WAV. Ambience is stereo 48 kHz Vorbis at 128 kbps using FFmpeg 9's native encoder. Preparation measures mean/peak levels, limits normalization boosts to 18 dB, applies authored family gain, and limits peaks. One-shots remove leading silence below -55 dB; recipe segments and short terminal fades bound duration. Loops bake a 250 ms equal-power wrap seam and record decoded loop bounds. Originals are preserved.

The separate typed `audio/manifest.json` records IDs, relative content-addressed paths, hashes, sizes, durations, channels, sample rates and loop boundaries. Accepted source/processing receipts are preserved in the repository snapshot metadata. Identical cooked bytes share files. Runtime selection, bundle publication and asset checks include all selected audio and verify hashes; no runtime path points at Documents. Local prototypes use prepared layers. Successful preparation accepts the new repository snapshot under [preparation and publication](assets.md#preparation-and-publication). Pins without an audio manifest build and preview silently. Present manifests and their samples still require schema and integrity validation.
