# Verification

## Regular checks

Choose the command for the evidence needed:

| Command              | Coverage                                                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `npm run check`      | Typechecking, JavaScript/TypeScript linting, handwritten code formatting and fast pure suites. Required after edits stabilize. |
| `npm run docs:check` | Documentation links, anchors, script names, file references and guide reachability. Also required for prose edits.             |
| `npm run check:ci`   | All regular source checks, all pure suites, documentation, repository/import boundaries and unused-code analysis.              |

`check` and `check:ci` run each selected phase fresh, report timings and fail on the first broken phase. Previous passing results never suppress a selected suite. These commands do not acquire artwork, run browser or desktop checks, package the application or install Python tooling. `check:ci` can run locally; it does not establish a hosted CI result. Follow [test selection](#test-selection) for those integration tiers and [documentation checks](#documentation-checks) for prose accuracy limits.

## Visual acceptance

Substantial UI, layout and artistic changes require inspected rendered before/after evidence at intended usage scale. Follow the [frontend workflow](../.agents/skills/frontend-design/SKILL.md) or [scene workflow](../.agents/skills/lantern-scene-design/SKILL.md). Check relevant constrained layouts and interaction states. Inspect transitions in motion when changed. Keep captures outside Git and disposable worktrees, and link the durable location from the task report or [reference index](../references/visual/README.md) when reusable. Missing rendering leaves visual acceptance unverified. Browser assertions, source checks and asset metadata do not establish aesthetic quality or human preference.

## Test selection

`npm test` and `npm run test:watch` default to fast `tests/unit/*.test.ts` suites. `npm test -- --full` runs all pure suites; `npm run test:watch -- --full` watches them all. The small explicit CI-default list in `tools/test.ts` keeps fresh-process replay/build proofs, real-Git integration-lock proofs and long cache contention checks in full CI coverage; it records each reason, and missing entries fail selection rather than silently losing coverage. New pure suites run locally unless deliberately classified. Arguments name exact files, including CI-default suites; duplicates run once and invalid selections fail before setup. Use `--full` without exact files or `--assets`. Pure tests use small fixtures and require no source artwork or prepared pack.

Routine runs execute suites serially in one Node runtime, sharing TypeScript startup and module loading. Tests must restore global mocks, environment changes and acquired resources after each case. Full, asset and watch runs retain separate suite processes with concurrency two; full CI also checks independence between suites.

Compiler fixtures use a 32 × 36 canvas and 64-pixel atlas. One tiny multi-page packing case checks RGB alpha synthesis and asymmetric pixels at every published rectangle, protecting row/page rollover, orientation and channel order in a single encoding pass. Determinism and failed builds compare both manifest and page bytes, including a missing later frame after an earlier frame has been packed. Keep these behavioral checks when changing fixture sizes; large uniform images add cost without exercising more encoding behavior. HTTP identity fixtures close their completed connections explicitly instead of waiting for keep-alive expiry.

Routine local testing should take roughly ten seconds including setup. This is a guideline, not a timeout or permission to omit failures. Optimize useful slow tests or route them to CI by default. Asset, browser and desktop checks are explicit integration commands, outside routine local checks. Agents may run full or slow coverage locally for a specific reproduction, diagnosis or validation need: state the reason, choose the smallest relevant scope and avoid repeating unchanged successful runs. Changed browser behavior needs appropriate CI scenarios; report whether they actually ran, including pending or unavailable coverage.

Authored scenes are disposable content: gameplay and rendering regressions own their setup, and authored-document validation accepts an empty scene directory. The explicit full artwork audit validates saved documents through `checkSceneDocuments`; pure tests cover placement rejection with small fixtures instead of repeating a sweep of mutable editor saves.

`npm run test:assets` runs `tests/assets/*.test.ts` against pinned prepared assets. Authored scene documents validate against authoring assets independently of Game selection. Python authoring/recovery fixtures belong to this tier and require Pillow. CI installs Pillow 13.0.0 in a temporary environment before the tests; test commands do not install dependencies. For local asset tests on macOS/Linux, create or reuse a checkout-local environment and activate it so subprocesses find Pillow:

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install Pillow==13.0.0
npm run test:assets
```

CI uses `npm run test:assets -- --built` after `npm run build`. It verifies and copies the delivered Game artifact into an isolated test workspace, authenticates only the native hero receipt from the pin, and runs animation-treatment, hero-art, Oracle-art, library-import and source-recovery suites. `npm run assets:check -- --built` validates the active Game catalog's actual image bytes, clips, calibration, audio and lighting registration. The full legacy-art/library sweeps remain available through the commands without `--built`; full CI deliberately omits them. Both built commands reject missing or mismatched artifacts.

The fixtures invoke `python3`, which must resolve to the environment containing Pillow. Full [asset preparation](assets.md#local-preparation-review) needs additional authoring dependencies; the local selection models have [separate setup](developer-tools.md#local-foreground-selection-setup). `npm run assets:check` validates current runtime manifests, references, pages and companion registration without source-library access or visual approval.

`npm run test:browser -- [scenario]` runs Playwright scenarios in `tests/browser`:

| Selector                             | Coverage                                                                                                                                                                                                               |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `game` (or `game-loot` for labels)   | Input, pause/focus, checkpoints, orchard rewards, branching Orchard/Clearing/Forge travel and reward persistence, distant loot-label routing, and chapel entry, reward retention, retry and matching forge return with neither, either or both kit upgrades. |
| `scene`                              | Independent outdoor/interior fixtures, reload and resource lifetime.                                                                                                                                                   |
| `editor`                             | Authoring, history, reload, ground interaction, contact shadows and protected save requests.                                                                                                                         |
| `effects`                            | Dedicated-scene controls and switching back to independent scene fixtures.                                                                                                                                             |
| `audio`                              | Prepared-sample decoding, localized ambience and Dev Preview audition controls; Game settings share `game-motion-blur`.                                                                                                                            |
| `image-delivery`, `ground-occlusion` | Focused GPU behavior.                                                                                                                                                                                                  |
| `authored-ground`                    | Opt-in [movement and timing capture](developer-tools.md#authored-scene-timing-capture), selected by `LANTERN_GROUND_SCENE`.                                                                                            |
| `ground-review`                      | Opt-in [occlusion captures](developer-tools.md#authored-occlusion-captures), selected by `LANTERN_GROUND_REVIEW`.                                                                                                      |
| `orchard-design`, `orchard-polish`   | Opt-in [opening composition and effect captures](developer-tools.md#opening-comparison-captures), with external output directories.                                                                                    |

Without a selector, Playwright selects all browser suites; capture/review suites skip unless their opt-in environment variables are set. Selectors match filenames, so `editor` includes the editor regression, ground, contact and gameplay-authoring suites. Development-only UI and renderer lifetime regressions belong to `scene`; the built Game runs cannot import their failure-injection modules. Add `--list` to inspect the selected cases without acquiring assets, taking the GPU lane or starting a preview; built-Game discovery needs no existing build. Multiple selectors can share one run, for example `npm run test:browser -- scene image-delivery ground-occlusion audio`.

Use `npm run test:browser -- --ci-development` for the complete retained development-browser CI tier, adding `--authoring` to include editor/effects suites. This selection excludes Game and opt-in captures; run `game --built` separately against a production web build. The same `--list` discovery option works with tier selection.

The `audio` decoding and audition tests skip when the selected assets contain no prepared samples. To validate unpublished sounds locally, use a checkout-local [audio preparation](assets.md#audio-preparation) and leave `CI` unset; pinned CI cannot establish coverage for those samples. Browser decoding and playback assertions do not establish an audible mix; follow [listening and tuning](sound-design.md#listening-and-tuning).

Development-preview browser checks prefer checkout-local prepared assets, falling back to the pin. One preview session acquires assets and starts a server, or reuses a matching Vite server after checking checkout, asset identity and required scope. It closes only its own server and lease. With `CI=true`, browser checks use pinned assets and require an unused port for their own server; use this mode for [milestone verification](release.md). Install Chromium once with `npx playwright install chromium` when needed; Linux hosts may also need Playwright's `--with-deps` installation. Add `--ui` after the scenario for continuous interactive iteration, for example `npm run test:browser -- editor --ui`.

After `npm run build`, `npm run test:browser -- game --built` verifies Game against the production web artifact with its recorded asset identity. It checks artifact bytes before starting a dedicated preview, without reopening the asset cache. Scene/editor/effects scenarios retain development previews because production Game excludes those views. Game packaging replaces the web identity with a combined desktop identity; run `npm run build` again before using `--built` after Game packaging.

`npm run test:desktop` consumes a Game package and tests the actual executable, bundled identity, real controls and storage restart. The live-development fixture copies sources and installed dependencies into an isolated checkout, excluding generated dependency caches; CI verifies fresh installation once before these tests. Native results apply to the platform exercised. Browser results do not certify desktop integration or visible reference-hardware pacing.

Non-watch `npm test` and `npm run test:assets` omit individual passing cases while streaming summaries, failure details, skips, TODOs, stdout and stderr through Node's spec reporter. `--verbose` restores passing-case output; watch mode always includes it. Reporting does not change suite selection or failure exit status. Browser and desktop tests use their own reporters.

## Opening playtest

Use a fresh player profile and the production Game view with default visual/audio settings for agent-driven gameplay review. Controls remain available in pause/help. First-time player testing is outside the current roadmap and is not an acceptance gate. If a first-time player becomes available later, an optional uncoached session can assess understanding; agent-driven journeys do not establish that result.

Explore both Orchard branches and the Forge–Chapel connection in both directions. Record hesitation, missed entrances, backtracking, inaccessible apparent floor, unreadable hits and confusion about adjacent destinations. Check the shed floor, clearing stairs and terraces, forge workshop and rooms, and chapel altar and entrance stairs with the moving hero visible. Verify physical departures during pursuit and containers near living enemies. For an optional human session, ask what the player understood after play rather than explaining it during play.

Cover buying sword first, lantern first and eventually both improvements. Earn encounters and resources through ordinary play; do not seed victories, grant items, teleport or change combat defaults. After choosing, compare the upgraded kit against restored encounters. Exercise death/retry and save/resume without losing earned improvements or rewards. Preserve observations and requested captures outside Git, including source/asset identity, choice, settings, interruptions and any coaching. Fix the largest observed friction before expanding the adventure; distinguish observed defects from design hypotheses.

The [audio listening pass](sound-design.md#listening-and-tuning) is deferred until the user has time. Run [Windows acceptance](release.md#opening-windows-acceptance) on the named target host when available. Report audible mix and target-hardware checks separately from functional browser coverage; neither is established by agent-driven browser checks.

## Test value

Write and retain only high-value tests: detecting a plausible, significant failure must justify the effort to write and maintain the test and the time to run it, including setup. This applies across gameplay, saves, rendering, assets, tooling and delivery. There is no test-count quota or line-coverage target.

Before adding a test, identify the failure it catches and inspect existing protection. Extend an existing test when that provides clear coverage more cheaply. Zero new tests is appropriate when existing coverage is sufficient or a proposed test offers insufficient value. Do not add medium- or low-value coverage: trivial implementation assertions, redundant cases, source-text checks where behavioral proof is available, or speculative edge cases without meaningful consequences.

Protect a consequential failure once at the cheapest sufficient layer. Prefer observable state changes, failed operations, cancellation, re-entry and disposal. Keep expensive integration tests only for failures cheaper tests cannot meaningfully catch. Consolidate overlap, strengthen or remove weak tests, and remove coverage for removed machinery; preserve meaningful known-regression, exact rendering and resource-lifetime protection when its value justifies the cost. Review a plausible broken implementation against the assertion before claiming protection.

Do not add retries to hide races, silently skip failures or weaken an invariant to reach a timing target. Test value is a review judgment; duration alone does not establish it.

## Code formatting

`npm run format` and `npm run format:check` handle handwritten JavaScript/TypeScript, CSS and HTML in the repository root, `src/`, `electron/`, `tools/` and `tests/`. Markdown, authored JSON and canonical art/reference files are not reformatted. Explicit Python formatting uses `npm run format -- --python`, which also formats the regular code selection; set up the authoring environment first. Use `npm run format:check -- --python` to check both without writing.

## Linting and unused code

`npm run lint` runs Oxlint with TypeScript awareness. `npm run knip` checks live entries and dependencies. Python authoring lint is explicit: after installing Ruff 0.16.10 in the checkout's `.venv`, run `node --import tsx tools/lint.ts py`. This uses the repository's handwritten-file selection and Ruff configuration; `--fix` applies supported fixes. Python formatting uses [the explicit Python option](#code-formatting). Keep entry declarations aligned with real HTML, CLI, test and preparation consumers.

## Documentation checks

Run `npm run docs:check` after documentation edits; `npm run check` does not include it, while `npm run check:ci` does. It validates local Markdown links/anchors, npm script names, repository file references and reachability of root/docs guides from README or AGENTS. It does not validate command arguments, external links or whether prose matches behavior. Check those claims against the relevant source owner. Feature guides link to the relevant workflow or contract owner.

## E2E coverage and execution budgets

Routine Linux CI runs all pure suites and source gates first. One Linux build produces the verified Game web artifact for every Game shard and both native packaging jobs. Uploads retain the build identity and exact bytes; consumers reject changed files or another commit. Native packaging also compares current web inputs before adding its platform-specific Electron bundle. The complete manual workflow includes assets, authoring and both native platforms.

Eleven Game shards cover controls, a native camera strip, inventory, upgrades, loot-label routing, adventure rewards/travel and one complete upgraded-kit chapel entry/reward/retry/return journey. Pure progression tests own upgrade permutations; the same browser journey is no longer repeated four times. Audio and graphics settings share one persistence/reload journey. The camera strip retains native pixels at one wide viewport; the former three large screenshot variants are removed.

Sixteen development-browser shards use `--ci-development --ci-shard=N/16`, adding `--authoring` for editor/effects changes. Discovery enumerates every retained test before balancing expensive cases across shards. Nested and parameterized titles stay distinct, and unclassified suite names fail selection. The relative costs in [the shard planner](../tools/ci-browser-shard.ts) are scheduling estimates, not performance results. `--list` shows the selected shard without assets or a preview. One browser worker and a fresh process per case preserve isolation; no test retry is enabled. Hosted logs include each case's elapsed time.

Tests explicitly choose their evidence boundary. `pixelTest` runs real WebGL draws at native device resolution for image delivery, camera artwork, editor/Game parity, contacts, outlines, occlusion, lighting, motion blur and batching. `stateTest` exercises real browser DOM, input, contexts, asset upload, shader compilation and ownership, but suppresses the four WebGL draw entry points: its unused framebuffer is not renderer evidence. It uses quarter-resolution buffers with unchanged CSS geometry. `LANTERN_TEST_RASTERIZE=true` restores draws and `LANTERN_TEST_SCALE=1` restores native resolution for diagnosis. Capture requests restore both automatically. The shutter proof uses a small native viewport with unrelated lighting/shadow/bloom passes disabled and encodes PNGs only for requested captures. Packaged Game smoke keeps real native draws on its first launch at half device scale. Its checkpoint-restoration launch and live-development watcher journey use the state fixture; `LANTERN_TEST_RASTERIZE=true` restores their draws. Native tests do not establish visual acceptance.

Repeated browser locomotion matrices are removed; pure heading/phase matrices and the real eight-direction input case remain. Editor/Game parity uses one outdoor and one interior painting. Ground authoring retains refined mask acceptance, brush undo, save and profile restoration; repeated pointer, invalid-polygon and movement journeys are omitted. The source-art exploration routes and videos remain an opt-in `editor-exploration` review through `LANTERN_EXPLORATION_CAPTURES`, alongside the existing composition/capture suites. These reviews do not run in full CI.

Dependency setup caches immutable asset entries by asset pin, platform and job partition. Live leases are excluded. Restored bytes still pass the asset workspace's normal hash checks. Game shards consume the artifact directly, without reopening the asset cache. Development previews acquire pinned files on demand. The asset job consumes the same Game artifact and one authenticated metadata receipt, retaining current Game compatibility and Python import/recovery proofs. It no longer materializes the 23GB authoring library. Asset/content/presentation/delivery changes select it; manual dispatch always includes it. Explicit `test:assets` and `assets:check` retain the broader artwork audit outside CI.

Desktop/build/dependency/delivery changes select both macOS and Windows packaging and executable tests, including real storage/input, renderer reload, independent main/preload restart and owned shutdown. [Coverage policy](../tools/coverage-policy.ts) owns optional selection; an unavailable comparison base selects all tiers. The final [workflow check](../.github/workflows/ci.yml) fails on any failed or cancelled selected job.

Browser assertions allow 30 seconds for software WebGL, with explicit longer deadlines for scene replacements. Screenshots, video and traces are off unless requested by a suite. Failure output includes startup stages, pending requests and renderer errors. Captures and failure artifacts stay outside Git. Playwright clears `.cache/browser-results/` at the next run, so copy needed evidence externally first.

The elapsed target is under ten minutes; report observed hosted timings rather than inferring a result from shard count. Separate cold acquisition, cache upload/restore and runner queues from test execution. Full-library validation and native hosts can remain the critical path. Hang deadlines are independent of this target. Local GPU tests and asset preparation share the [command lane](task-coordination.md#concurrent-commands); source checks and builds do not. Unit concurrency remains two and browser concurrency one.

## Diagnostics and measurements

The `benchmark` command routes several kinds of diagnostic. [Recorded session replay](session-replay.md) covers the headless `record` and `replay` modes; `compare` reads saved measurement records. `walking` is the default quick native measurement; `editor` runs the browser editor scenario. `quality` checks prepared asset metadata, source-density declarations and texture budgets without launching a renderer or requiring a package; it does not establish visual quality. These modes are separate from the native scenarios below.

Native diagnostics consume an already packaged application; they do not build it. Prepare the matching package on the host before running a scenario:

| Scenarios after `npm run benchmark --`                                          | Required package                      |
| ------------------------------------------------------------------------------- | ------------------------------------- |
| `startup`, `walking`, `pacing`, `journey`, `game`, `preferences`                | Game: `npm run package -- --unsigned --inspectable` |
| `sandbox` (alias `scene`), `lighting`, `animation`, `hero`, `effects`, `scenes` | Dev: `npm run package -- --dev`       |

Game native diagnostics require `LANTERN_EXECUTABLE` to select the separate inspectable executable under `release-inspectable/`; see [diagnostic builds](release.md#package-hardening-and-diagnostic-builds). Release desktop tests continue to use the hardened Game package.

Use `--local` on both packaging and the diagnostic when investigating a local asset preparation. `--visible` shows the native window; hidden/software runs do not establish visible pacing. Use `--capture` when visual evidence is wanted, or `--output /external/investigation` to retain results without requesting captures. Successful managed diagnostics normally discard their output; keep comparison records in an external directory. Native framebuffer, motion and resource assertions remain available through these scenarios; routine checks do not generate galleries.

For an opt-in browser failure trace, pass `--trace retain-on-failure` after the scenario, for example `npm run test:browser -- game --built --trace retain-on-failure`. This records the failing first attempt without enabling retries. Copy retained traces externally before the next run clears the output directory. Traces diagnose DOM, requests and assertions; a state fixture still does not establish rendered pixels.

Initial goals are three seconds for warm preview updates and ten seconds for ordinary checks; correctness remains required.

## Performance comparisons

Compare cold acquisition/startup separately from warm iteration, checks, builds and packaging. Use repeated equivalent samples; record hardware, assets, settings, sample duration, foreground/background policy and rendering quality. Count transferred bytes and repeated launches as well as elapsed time. Preserve needed baselines outside Git.

`npm run benchmark -- sandbox --benchmark --output /external/renderer-baseline` retains renderer measurements in that directory’s `benchmark.json`; `npm run benchmark -- compare <baseline.json> <candidate.json>` compares retained external records. Benchmarks require a package matching current desktop build inputs and the selected asset pin; records keep source and build identities separately. Harness-only edits do not require recompilation. Renderer calculation changes require native output and exact pixel parity. Fewer submissions alone do not prove better visible pacing.

## Quick walking measurements

After `npm run package -- --unsigned`, run `npm run benchmark` for one hidden hardware-rendered walking sample: one second of warmup, then five seconds holding forward in the current Game starting scene at the display’s logical dimensions and render scale 1, with depth of field at 100% and every player visual-effect toggle enabled. The command retains `benchmark.json` outside Git and prints its path, actual framebuffer dimensions, GPU, refresh rate, FPS, p50/p95/p99 and worst frame intervals, intervals over 25 ms, and absolute/normalized hitch (≥50 ms) and stall (≥100 ms) counts. Use `npm run benchmark -- --output /external/walking-baseline` to choose a retained directory. `npm run benchmark -- walking` is equivalent. Add `--visible` for a borderless fullscreen confirmation run (simple fullscreen on macOS), with the complete viewport fitted to the display. Hidden and visible records cannot compare with each other.

On macOS the quick path requests ANGLE Metal and rejects software fallback. Quick results and temporary profiles use a separate external `-measurements` cache capped at 256 MiB, avoiding artwork-cache scans on every run. The packaged executable supplies all assets; pin lookup does not acquire artwork payloads. The quick path skips the loading-media, menu and checkpoint journey checks. It verifies actual movement, hardware GPU observations, foreground sampling for visible runs and stable settings/source inputs. It consumes a matching package and rejects stale builds; packaging is explicit and outside the measurement time budget. It fails immediately if the GPU lane is occupied. The hidden default has a 27-second subprocess deadline and one-second termination grace for a 30-second command budget on a prepared, uncontended host. Visible confirmation permits up to 60 seconds for fullscreen setup and validation. A busy machine can prevent a result within that budget; the command prints total wall time on success or failure. Do not substitute software rendering or reduced resolution to meet the time goal.

For a visible run at a reported 59–61 Hz refresh rate, the provisional target is at least 59 FPS, p95 ≤18 ms, p99 ≤20 ms, no hitches and no stalls. Hidden runs and other refresh rates report the 60 Hz target as inconclusive. Frame callbacks measure cadence, not GPU execution or display presentation; a five-second sample cannot rule out rare stutters. Repeat matching runs before claiming an improvement. `compare` accepts walking records but refuses comparisons with the full journey or different conditions.

## Packaged player journey measurements

Pacing records distinguish intervals at or above 25 ms from estimated missed refresh slots. The latter derive from callback gaps and do not establish physical presentation. Threshold comparisons normalize sub-nanosecond timestamp subtraction residue; raw intervals remain unchanged. Brief window blur or hidden-document transitions reject a trial even between frame callbacks. Opening ability/dodge checks run before the sustained input loop, with their checkpoint and partial recording retained on rejection.

`npm run benchmark -- pacing --visible --samples 5 --duration-ms 60000 --output /external/pacing` measures seeded encounters in each playable area plus a clustered Orchard stress fixture, at render scale 1 and the package's normal effect defaults. It verifies movement, accepted lantern/dodge cooldowns and enemy response through real checkpoint controls. `--scenario <area-id>` or `--scenario stress` selects one fixture. Add `--baseline-executable /path/to/baseline` for alternating retained-baseline/current-candidate runs with the same asset pin. Records retain package identity, settings, input sequence, framebuffer, hardware renderer, foreground observations and every active frame gap. `compare` rejects different conditions or incomplete work. The 60 Hz target is ≥59 FPS, p95 ≤18 ms, p99 ≤20 ms and zero intervals ≥25 ms; a single sample is diagnostic only. Loading/menu intervals are retained separately. These seeded input loops do not establish an uninterrupted full-adventure playthrough.

`npm run benchmark -- journey --visible --capture --soak-ms 900000 --output /external/journey` checks loot collection, equipment, a real campfire upgrade purchase, rest, death/retry and outward/return area transitions. Checkpoint-assisted positions and cleared encounters isolate UI and room lifetimes; combat pacing remains the separate `pacing` diagnostic. After the first loop, the soak sustains movement and effects between linked transitions until at least fifteen minutes of active arrival gameplay have completed; loading and menus do not fill that budget. Reports retain phase-specific callback intervals and completed behavior checks. Captures and profiling run outside measured encounter intervals. Neither mode certifies Windows or display presentation from callback cadence alone.

Renderer CPU/GPU query instrumentation is disabled during normal gameplay. Separate Dev Preview profiling explicitly enables `presentation.lookRenderer.setProfiling(true)` and disables it afterward. Native painted-shadow parity can run the same `tests/fixtures/shadow-batching.ts` proof as the browser suite; it compares the original contour submissions with region batches across all four areas and moving local lights.

`npm run benchmark -- startup --samples 5 --visible --output /external/startup` measures fresh-process Game startup for empty storage and checkpoints in each current area, then verifies immediate attack, dodge, movement and lantern activation through the saved gameplay state. `--scenario fresh` restricts the run to empty storage. It records launch and document observations, overlapping registration/image/companion/GPU stages, resource timings, build identity, hardware and first-action frame cadence. `--baseline-executable /path/to/baseline` alternates matching baseline/candidate samples. Baseline packages must use the same asset pin; candidates must match current desktop inputs. Use 20 samples per scenario for a p95 below 10 seconds acceptance claim on reference Windows hardware. Fresh profiles do not establish an OS-cold disk cache, and macOS observations do not qualify Windows. Full quality and real input acceptance remain required.

`npm run benchmark -- game --benchmark` exercises movement, action inputs and checkpoint operations in the selected Game package after explicit packaging. It does not measure encounters, connected-area traversal or death/retry. Its fixed movement and action journey does not establish combat performance for the authored encounters. Preserve gameplay, animation timing, sound behavior and visual fidelity. Hidden/software runs do not certify 60 FPS on reference hardware or visible polish. See [Delivery](release.md) for packaging and [session replay](session-replay.md) for headless reproduction.
