LANTERN KNIGHT: INITIAL FOUNDATION ASSIGNMENT

Build the foundation of a new fixed-camera, 2.5D dark-fantasy action RPG using three.js and Electron. Deliver three connected results: an asset/animation test room, a controlled production pipeline that creates and integrates one usable walk loop and one sword attack before expanding to eight directions and the remaining clips, and a small playable encounter. I want to replace rough assets with finished art without rewriting movement, combat, scene composition, or the renderer.

1. CONFIRMED DIRECTION AND PROVISIONAL CHOICES

- three.js rendering and Electron desktop shell.
- Fixed camera orientation. Camera translation/follow is allowed; player-controlled orbit or rotation is outside this assignment.
- A 2.5D presentation: directional animated character sprites, carefully composed environment art, and simple underlying 3D geometry where useful for ground, collision, depth, and lighting.
- A male Lantern Knight as the initial hero, carrying sword and lantern. His visual design is not approved yet. The latest direction calls for lighter, less chunky armor and a more distinctive, handcrafted character; do not lock the current concept's heavy plate, topknot, or palette.

- Clean, stylized, graphic/cut-paper shapes and readable silhouettes. Hades, Absolum, Hollow Knight, and Silksong inform visual clarity and shape language; Diablo II and Path of Exile II inform dark-fantasy atmosphere. Create original art direction rather than copying characters or assets. Avoid muddy detail, noisy realism, indiscriminate bloom, and darkness that obscures combat.

Provisional defaults, to document and keep configurable:

Keep those sides consistent in every direction. Include attachment/event metadata for lantern effects. Full interchangeable equipment is future work.
- One small hand-authored room, one simple melee enemy archetype, one attack, one dodge, one ability, damage/death/reset, and a minimal health/cooldown HUD.

Do not block ordinary groundwork on reversible choices. Ask only when an unavailable input or a consequential decision actually blocks progress. Keep provisional decisions visible. 3. FIRST CONTRACT: CAMERA, WORLD, SCALE, AND DIRECTIONS

Create a versioned camera/asset-space contract that is consumed by the asset compiler, runtime, and calibration scene. It must describe projection, orientation, world axes, source image coordinate convention, anchor convention, source pixel density, baseline framing, and the asset bake version.

Use a right-handed world with XZ as ground and +Y as height. Define azimuth unambiguously: measured from +Z toward +X around +Y. For the initial camera proposal, its horizontal offset from the look-at target is in the +X/+Z quadrant. Define elevation above the XZ plane. Include the actual camera basis/matrix in a machine-readable calibration fixture rather than relying only on the word "isometric."

Use an orthographic camera with a documented vertical span and resize policy. Keep vertical world framing stable while horizontal coverage follows aspect ratio, unless there is a recorded reason to letterbox. Separate logical viewport size, drawing-buffer resolution, device pixel ratio, and optional render scale. A Mac Retina window must not silently render four times the intended pixel count. Fix orientation for normal play; camera follow moves the camera and its target together. Avoid unrequested zoom changes.

Record the exact asset bake orientation. Use one approved fixed-camera bake contract for the playable content; do not produce duplicate asset sets for multiple camera angles. Camera comparisons can use the same actual 3D calibration proxy before approval. Changing camera azimuth/elevation or the asset projection contract requires a version change and regenerated/revalidated dependent assets. Never "fix" a camera mismatch with undocumented nonuniform sprite scaling. Treat deliberate presentation zoom and higher-resolution exports separately from a bake-angle change.

All actors have a simulation foot position on the ground. Visual quads, shadows, aim indicators, and collision debug views derive from that position. The image anchor is measured in the original untrimmed canvas, with pixel origin at top-left, +x right, +y down. Store the original canvas size, trim rectangle, anchor, and any extra padding. Trimming must preserve placement exactly. For a camera-facing quad, reconstruct trimmed bounds relative to the untrimmed anchor using the declared pixels-per-projected-world-unit, then place the anchor at the projected foot. Do not treat image height as world-Y height without accounting for the bake projection.

Choose source resolution from the hero's actual on-screen footprint at the baseline framing, including room for the sword, lantern, and effects. Document the calculation: projected screen pixels per world unit = drawing-buffer height / effective orthographic vertical span. Distinguish that runtime density from source pixels per projected world unit. Make art at a sensible oversampling factor, not at an arbitrary giant resolution. Do not enforce a 512-pixel canvas if a smaller source is enough. Start with one consistent per-character canvas and density; use metadata to support trim differences.

Define eight headings numerically. Use labels d00, d45, d90, d135, d180, d225, d270, d315, with heading zero = +Z and positive rotation toward +X; yaw = atan2(direction.x, direction.z). The artwork must show the character facing that world heading under the recorded camera. Add screen-arrow and front/back labels in the viewer so artists cannot confuse world headings with screen compass directions. With the proposed camera, d45 faces toward the camera/screen-down and d225 away/screen-up. Verify this rather than guessing from filenames.

Implement one tested direction-selection function with wraparound, consistent tie handling, and small hysteresis if needed. Aim is continuous simulation data; visual facing is quantized. Aim uses a pointer ray intersecting the ground plane, correctly accounting for canvas position and resize. Normalize diagonal WASD motion. Explicitly choose screen-relative movement projected onto XZ as the initial control convention, show the mapping in the lab, and keep it configurable.

Acceptance fixture: a marked grid, unit cube, axis arrows, footprint marker, eight-way facing chart, and a representative hero silhouette. Test projecting and unprojecting ground points, foot anchoring across clips/directions, trim invariance, and resizing. Include screenshots at baseline 16:9 plus a second aspect ratio. Label the camera version and provisional angles on calibration screenshots.

4. ASSET PIPELINE: SOURCE TO VALIDATED RUNTIME CONTENT

Create the schema before adding many assets. Use a runtime-validatable schema with useful file/field errors, generated or checked TypeScript types, and an offline compiler. Avoid a schema library that requires a large application framework. The precise folder names are your choice; preserve these distinct stages:
- References/concepts: mood boards, generated concepts, exploratory sheets. Never implicitly import these into the game.
- Authoring sources: editable source files or original renders, provenance/license, and bake recipe when available.
- Import staging: reviewed, consistently exported PNG frames or equivalent lossless inputs plus source metadata.
- Generated runtime assets: reproducible atlases, compiled manifest, hashes, contact sheets, and build report. Treat these as generated output, not hand-edited truth.

The compiler should ingest real exported frames, validate them, preserve anchors, trim safely, pack atlases deterministically, and emit runtime data. Keep this separate from the focused authoring/export pipeline required below; do not build a general rendering farm or image-generation service. If no finished frames are provided, begin with clearly labeled diagnostic sprites with asymmetric sword/lantern markers, feet, direction labels, and several distinct frames. They unblock the runtime while the controlled walk/attack production pipeline is built; they are not the final animation deliverable. Do not treat a tiled AI concept image as an automatically valid sprite sheet. A single illustrated pose is not an animation set.

Define at least:
- Asset ID, type, schemaVersion, contentVersion/hash, bundle, provenance/license, and placeholder/production status.
- Camera/bake contract ID, source canvas dimensions, projected pixel density, foot anchor, trim bounds, color space, alpha convention, and import recipe/version.
- Atlas page ID, image path/hash/dimensions, per-frame rectangle, rotation flag, extrusion/gutter metadata, and original-source mapping.
- Character clips, direction entries, explicit ordered frames, frame durations, loop behavior, visual notifies, and supported fallback mappings.
- Render category, contact-shadow settings, optional attachments, occlusion/depth metadata, and collision footprint references. Collision shapes are authored gameplay data, not inferred from alpha bounds.
- Dependency and bundle membership, size estimates, and required versus optional resources.

Use stable IDs and explicit ordering. Never rely on directory enumeration or lexicographic frame sorting for playback. Reject duplicate IDs, non-finite values, zero/negative frame durations, broken references, out-of-bounds atlas rectangles, wrong image dimensions, incompatible camera contracts, missing required headings/clips, invalid anchors, and unapproved production placeholders. A ground anchor outside the visible opaque region can be intentional; validate its declared coordinate convention rather than requiring it to sit inside the alpha silhouette.

The first tooling commands should cover validation, compilation, and a contact-sheet/inspection report. Compilation should be deterministic from identical source inputs and tool versions, with output written safely so a failed build cannot leave a half-updated manifest. Restrict source paths to the approved asset roots. Enforce exact filename/path case in references and reject paths that differ only by case, so content remains portable across Windows and macOS filesystems. Build a tiny valid fixture and deliberately invalid fixtures for the linter.

Atlas policy:
- Begin with conventional RGBA PNG pages and explicit color metadata. Use a practical starting page size, such as 2048 x 2048, and a configured maximum verified against renderer capabilities. Split pages rather than assuming an unlimited texture size.
- Do not rotate packed frames in the first implementation unless the runtime and tests support it explicitly.
- Preserve a consistent straight/premultiplied alpha convention across import, filtering, shader, and blend state. Add edge-color dilation/extrusion and an adequate gutter; transparent black borders must not produce halos.
- Choose and document mip/filter policy. Do not assume a two-pixel gutter is safe at every mip level. For the fixed-scale first pass, a no-mipmap or carefully bounded-mipmap choice is acceptable if tested at expected scales; preserve clean downsampling and avoid shimmer. Do not force nearest-neighbor filtering merely because these are sprites.
- Keep per-instance frame UVs independent. Mutating a shared texture's offset/repeat must not make every actor switch frames together.
- KTX2/Basis texture compression is an optional later optimization after the PNG pipeline works. If adopted, validate alpha-edge quality, actual supported transcode formats, memory, bundled decoder paths, and offline loading. KTX2Loader support detection is required before loading [6]. It is not a first-milestone dependency.

Fallback policy must be explicit. Development can show a diagnostic missing-asset card or documented idle fallback with a warning. Production validation fails for missing required content or placeholders unless a deliberately named development-build flag permits them. Missing attack frames must never invent new attack timing or crash combat. Do not silently mirror asymmetric equipment, substitute directions, or hide missing production clips.

5. ANIMATION AND GAMEPLAY TIMING

Keep three clocks separate: fixed simulation ticks, visual clip time/frame durations, and render presentation. Use a fixed-step accumulator with interpolation, a bounded catch-up policy, and intentional pause/focus/suspend behavior. Avoid a huge simulation catch-up after an Electron window resumes. Input becomes simulation commands; deterministic tests must not depend on requestAnimationFrame timing, wall-clock time, or uncontrolled Math.random calls.

Initial hero state coverage: idle, locomotion, sword attack, dodge, lantern ability, hurt, and death. Support eight directions through the schema and diagnostic content. Prefer a small, clean frame set over hundreds of low-quality frames. For initial art planning, 8-12 visual FPS can be a useful starting range, with explicit authored holds and faster key moments where needed. It is not a cap on simulation responsiveness or a fixed requirement for every clip.

Use stable clip IDs and an explicit state-to-clip mapping. For compatibility with the optional draft art contract, the proposed IDs are idle, walk, run, attack_sword_01, dodge, hit, death, and cast_lantern_flare. Map gameplay "hurt" to hit and the provisional lantern ability to its selected clip; do not derive gameplay behavior from the name. A separate run clip can wait until the walk/attack proof works and the movement-speed design needs it. Draft clip rates and durations are tuning proposals, not user-approved timings.

Implement a small explicit state/ability model with transition and interruption rules. Put attack wind-up, active window, recovery, dodge movement/invulnerability, cooldowns, and hit-once-per-target behavior in gameplay definitions measured in simulation ticks or clearly converted time units. Bind the animation to that action timeline. Changing the number of visual drawings must not alter damage timing, movement distance, cooldown, or invulnerability.

Visual notifies are identified events such as footstep, swing whoosh, lantern flash, or dust. Specify crossed-interval behavior so frame skips still emit due events. Use an identity such as actor + action/clip instance + loop index + event ID to prevent duplicates. Define policies for looping, interruption, resume, and debug seeking. Scrubbing must not deal damage or replay sounds accidentally. If gameplay markers and visual markers share a data file, keep authority explicit: the simulation processes gameplay markers once; rendered frame changes do not cause gameplay effects.

Movement is simulation-owned and animations are initially in-place. Do not extract arbitrary root motion from sprite pixels. Keep action facing, movement facing, and aim as distinct concepts. For the smallest coherent animation kit, use travel-facing locomotion, aim-facing idle/attack/ability, and a facing lock when an attack starts. These are provisional animation policies. Eight forward-walk directions do not provide true aim-facing strafing or backward locomotion; do not make the hero moonwalk because the mouse points behind him. Torso-independent aim or dedicated backward/strafe clips can be a later expansion. Define dodge direction and its facing lock as tuning data. Smooth transform interpolation must not blend or warp art into unintended poses. Hold the final death frame and test repeated interruption/restart cases.

Build an animation lab with clip/direction selection, play/pause, frame step, timeline scrub, playback speed, foot/canvas/trim overlays, attachment markers, and a notify log. Show the authoritative action timeline beside the visual timeline. Reuse the actual runtime animator and assets so the lab cannot pass while the game uses a different code path.

6. DEPTH, OCCLUSION, MATERIALS, AND EQUIPMENT

Prove the scene-composition approach before creating a large environment library. Three.js transparent-object sorting alone cannot solve every overlap [4]. A tall flat sprite is not automatically a correctly occluding 3D object.

Define separate rendering categories for opaque ground/geometry, cutout actors and props, soft contact shadows, foreground/canopy pieces, and translucent effects. Choose one coherent initial depth policy and document the relevant depthTest, depthWrite, alphaTest/blending, and stable sorting settings. For mostly hard-edged art, alpha-tested cutouts are worth testing; retain intentional soft edges and show the tradeoff. Blended effects need their own depth-write/sort treatment. Do not disable depth testing across the entire game or patch individual overlaps with arbitrary renderOrder numbers.

Store foot/sort anchors and stable tie-breaks for actor/prop ordering. Tall or spanning objects need authored structure: split base/canopy/front/back layers, simple world-space occluder/depth proxies, or another demonstrated method. Pick the least complex solution that passes the test scene. Keep collision and visual occlusion separate. If using invisible depth proxies, verify that the proxy does not mask transparent holes or create an opaque rectangle around a sprite. Account for the mismatch between a camera-facing image plane and a world-space object's depth. Document unsupported overhangs/bridges instead of promising general depth from a single flat image.

Required overlap cases: hero crossing another actor; walking in front of and behind a pillar; passing partly behind a tree/canopy; walking beside a wall/corner; and a foreground element that can conceal the hero. Keep combat readable using a simple, bounded occluder fade or hero silhouette only if necessary. Show both normal and debug views.

Use correct color management: color artwork is sRGB; non-color masks/data have an appropriate non-color setting; output conversion happens exactly once [3]. Verify the same reference swatch and sprites in the import preview and runtime, over both dark and light backgrounds. Document the material choice for baked/painted shading so dynamic lighting does not double-light it. Begin with restrained lantern glow, readable world illumination, and soft ground-contact shadows. Do not assume a PointLight illuminates an unlit sprite material or that a sprite automatically casts the desired shadow. A contact-shadow decal is a valid first solution; align it to the ground and prevent z-fighting.

For the first hero, bake body, sword, and carried lantern into one synchronized visual set unless supplied production assets justify layering. Keep VFX separate through per-frame/direction attachment metadata, with a documented space and fallback. A hand/socket location in screen pixels is not automatically a world-space physical location; use an explicit mapping or an authored world-space approximation for lights and gameplay effects.

Document the future equipment contract without implementing every option: baked variants multiply clip/direction export cost; layered parts require identical bake camera, canvas, anchor, animation timing, per-frame attachment data, and per-direction front/behind-body ordering or masks. A lantern cannot simply be pasted above the body in every direction. Do not silently mirror the Knight and switch his sword/lantern hands. Include a rough asset-count/memory estimate for the initial loadout and the cost of another baked variant.

7. LOADING, LIFETIME, AND MEMORY

Build an asynchronous bundle loader with a manifest-first flow, deduplicated requests, shared-resource ownership/refcounts or equivalent explicit lifetime rules, progress/error reporting, and safe cancellation or stale-load suppression. Separate boot/UI, shared hero content, and room content. Load and warm required content before the encounter starts; avoid synchronous file IO, first-use decode/upload stalls, or compilation during the first sword swing where practical. A small preload/warm-up step is sufficient.

Unloading a room must release room-owned meshes, materials, textures, render targets, listeners, timers, and decoded image resources where relevant, without disposing resources still shared by the hero or UI. Removing an object from the scene alone does not dispose GPU resources [5]. Test an interrupted load followed by room replacement so late completion cannot resurrect a discarded room. Make retries safe and avoid an unbounded global cache.

Report file/download size separately from decoded CPU memory, estimated resident GPU texture memory, render targets, and temporary decode/transcode buffers. For RGBA8, width x height x 4 is a base-level estimate; include actual mip levels, atlas occupancy, copies, and additional maps. PNG compression does not directly reduce resident RGBA memory. renderer.info exposes useful object counts, not an authoritative GPU-byte meter [1]. Clearly label estimates.

Set provisional content budgets in configuration and a short document. A starting whole-scene texture budget such as 256 MiB may be useful, but label it provisional until a target GPU and full content set are known. Include hero, enemies, scenery, UI, effects, and post-process buffers; do not silently exclude the expensive category to pass. Prefer sensible source resolution, shared atlases, limited variants, and lifetime management before sophisticated batching. Run a short repeated room load/unload test and look for unexplained growth after caches settle.

8. ELECTRON SHELL, SAVES, AND PACKAGING

Keep Electron privileged work in main, expose a minimal typed preload API with contextBridge, and keep the game renderer free of Node/filesystem access. Explicitly enable contextIsolation and sandbox; disable nodeIntegration. Use a restrictive production CSP, packaged local content, blocked unexpected navigation/new windows, no arbitrary external URLs, and a bounded custom app protocol for packaged resources. Do not weaken these settings just to make the dev server work. Follow the current official security guidance [7-9].

Expose specific operations such as loadSettings, saveSettings, loadGame, and saveGame. Do not expose raw ipcRenderer, arbitrary channel names, shell execution, unrestricted filesystem paths, or IPC event objects. Validate request payloads and the expected sender/frame in main. The browser development adapter can use an in-memory or browser-local implementation of the same interface; tests must still exercise the actual Electron bridge.

Implement a small versioned save format for settings and the slice's minimal progression/state. Store it under the application's userData directory [10]. Use app-owned slot IDs, bounded payloads, schema validation, an atomic-write strategy appropriate to the OS, and recovery/backup behavior for corrupt or interrupted writes. Serialize concurrent writes. Separate save format version from asset schema version. Test a simple migration and graceful rejection of newer unsupported versions; never overwrite an unreadable save with defaults automatically.

Provide development and packaging commands for macOS and Windows using a supported packaging approach [11]. Keep paths portable and assets available offline. Verify a packaged build on the OS actually available. A successful macOS development run or creation of a Windows artifact does not establish a Windows runtime pass. Explicitly list unavailable platform checks; leave signing, installers requiring credentials, store distribution, and automatic updates for later. Do not claim release readiness.

10. TESTING AND BOUNDED PERFORMANCE CHECK

Automated coverage should include:
- Asset lint failures, deterministic compiler output, missing-resource behavior, camera/bake-version mismatch, trim/pivot math, angle wrap/ties, and invalid atlas data.
- Fixed-input simulation replay with seeded randomness and the same final state across different render cadences. Be precise about the determinism guaranteed; do not claim universal bit-identical cross-platform physics.
- Attack hit once per target, cooldowns, dodge windows, interruption/death transitions, skipped visual frames, looped notifies, scrub behavior, and independent actors sharing an atlas.
- Async cancellation/stale completion, shared resource lifetime, repeated room reset/load/unload, save validation/migration/recovery, and narrow IPC request validation.
- An available-platform desktop smoke test: boot, move/aim, attack/dodge/ability, resize, pause/resume, save/relaunch/load, and exit without new errors. Use current supported testing APIs [12].

Do a short, reproducible benchmark after the slice works: a brief warm-up followed by roughly a minute in a fixed-seed representative encounter, plus a separate modest stress fixture. Record exact machine/GPU, OS, Electron/Chromium and three.js versions, build mode, window/display refresh, actual drawing-buffer dimensions, render scale, actor/effect counts, and asset residency. Prefer packaged Electron for target performance claims. If only the browser/dev build or macOS is available, label that limit.

Report frame-time distribution (at least median and p95), visible stalls, draw calls/triangles, estimated resident asset bytes, and load/unload behavior. A 60 FPS target corresponds to approximately 16.7 ms per frame; 120 FPS to 8.3 ms. RequestAnimationFrame intervals are not pure GPU time, display refresh can cap them, and a browser-average FPS number does not prove Windows 1440p performance. Use GPU timing only if reliably available; mark it unavailable otherwise. Fix clear bottlenecks exposed by this pass, then rerun the same fixture. Do not build an hours-long profiling platform or make unsupported performance promises.

4. Refine one satisfying encounter and the lantern ability, then test the packaged Windows build on named target hardware before scaling content.

Do not label foundation success as final art approval or production performance certification. End with the most important next decision or blocker, not a long speculative feature backlog.
